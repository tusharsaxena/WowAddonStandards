> Part of the **[Ka0s WoW Addon Standard](../STANDARDS.md)** — the split standard. Cross-references use the `filename-§N` form (see the index's section map).

## Preview / test mode

Addons with a **positionable on-screen display** (a bar, an icon grid, a nameplate widget, a tracker frame, a window or popup the player places) **MUST** ship a **preview mode** (a.k.a. test / demo mode) that renders **representative placeholder data**, so the user can see and position the display without waiting for a real in-game event to populate it.

Reference implementation (in the collection): the modular tracker's cast bar shows a placeholder preview — a question-mark icon, a fake spell name, a `0.0 / 0.0` timer, and a bar filled to mid — **while the frame is unlocked**, so the user can drag it into place against realistic content.

- **SHOULD** trigger the preview automatically while the display is **unlocked** (drag/reposition mode), and/or via an explicit `/<slash> preview` (a.k.a. `test`) verb in the `COMMANDS` table (slash-commands-§3).
- **MUST** ship a **test mode** — the preview as a mode of its own, turned on and left on until turned off, independent of the lock, session-only, ended when combat starts and refused during it — and expose it as the **`Test mode`** checkbox in General → Master controls (options-ui-§15). A one-shot test verb MAY stay beside the mode but does not replace it. **Exception:** when unlocking already shows the display with its placeholder content, the unlocked view is the test mode and *Lock frame* is its switch — no separate test mode, row or `test` verb. A one-shot value hold, if the addon keeps one, lives at `/<slash> debug hold <value> [secs]`, which is not a test mode (options-ui-§15).
- **A test mode MUST say so on the display (v2.86.0).** While the explicit test mode is on, every display drawing placeholder data **MUST** carry a visible **text** marker saying it is showing test data. The marker:
  - is readable without hovering;
  - is localized (localization);
  - is visible in **every layout in which the placeholder data is visible**, a hidden header and a compact layout included.

  A display that is minimized with its header hidden shows no placeholder data, so it owes no marker in that state; the rule binds every layout in which placeholder data is visible. The measured failure: a meter window's test text rode its header and vanished with it when the header was turned off, while the sample bars stayed. **In a window or a HUD display the marker is the library's strip (MUST, v2.110.0)**, placed as *Where the strip sits*, below, says; on an unlocked HUD display the drag handle carrying the mode's tag MAY stand in for it (v2.114.0, the same paragraph). Any other display drawing placeholder data (a widget on a nameplate, a panel inside another addon's frame) chooses the marker's form: a badge, inline text, or the strip. A marker that overlays the display sits in the display's chrome band (frame-layering-§2); a strip that displaces content stays at the content's chrome level.

  **One marker per mode on screen (SHOULD NOT, v2.87.0).** Where a display shows the strip (standalone-windows), it **SHOULD NOT** also draw the same mode's word in its header. The header word, or a badge, remains the marker in any state that hides the strip but still shows the display, a minimized window or a load with no Widgets library, and in any display that has no strip.

  What is not a marker:
  - The launcher tooltip's `Test mode: On` and the Master-controls `Test mode` checkbox, because neither is on the display.
  - Placeholder data that merely looks plausible. Placeholder content whose visible text names the test **is** a marker on a display that is neither a window nor a HUD display. In a window it does not stand in for the strip (v2.110.0): a group popup whose placeholder content reads *Test Group — …* is a window, and carries the strip as well.

  The rule covers the **explicit test mode only**. Under the exception above, where unlocking is the preview and *Lock frame* is its switch, it does not apply. Missing, hover-only or layout-hidden markers are anti-pattern #97.

  **Where the strip sits (MUST, v2.110.0, owner rulings of 2026-11-15).** Every window and every HUD display that draws test or simulated data marks it with `LibKa0s-Widgets-1.0`'s **`TestStrip`**, in the library's amber for test mode and its cyan for a simulation (`kind = "sim"`), and the strip is placed by its own docking (LibKa0s-Widgets-1.0 Footer and TestStrip docking, Widgets minor 27, `LibKa0s v1.103.0`), never anchored by hand. A **window** is a frame with a title bar or header, a window background or a filter bar, whatever the addon calls it: a race or tracker window the addon names its HUD is a window, and so is a compact window that has hidden its header but still draws its body (standalone-windows). A **HUD display** is what the addon draws over the game world with no window chrome: bars, icons, icon grids, containers and HUD text.

  - **In a window, directly under the title bar.** The strip spans the window's full width inside its edge, directly below the title bar and above everything else the window draws: tabs, a filter bar, a toolbar and the body. While it shows, everything below the title bar moves down by `TEST_STRIP.HEIGHT`, and nothing is covered. The title bar carries no mode word while the strip shows (*One marker per mode on screen*, above). The heights are standalone-windows', *Window chrome geometry*.
  - **A minimized window, or one with its title bar hidden, keeps a marker.** A minimized window, its body collapsed into its title bar, hides the strip and carries the mode word or a badge in its title bar. A window that hides its title bar while its body shows keeps a visible marker in that layout, the strip at its top edge or a badge, because a marker never rides the header (the measured meter case above).
  - **On a HUD display, on its top edge and outside it.** The strip docks to the display's top edge, outside its bounds, where a window's title bar would sit, spanning the display's width, and flips under the display's bottom edge when the top would leave the screen. It takes no mouse, sits in the display's chrome band (frame-layering-§2) and moves with the display, so it never takes a click meant for the world. Each HUD display the player positions on its own carries its own strip. It never overlaps the drag handle an unlocked display shows.
  - **On an unlocked HUD display, the tagged drag handle MAY be the marker (v2.114.0, owner ruling of 2026-11-19).** While a HUD display shows its drag handle (`LibKa0s-Widgets-1.0`'s `DragHandle`) and the handle's label ends in the mode's localized tag (`TEST`, or `SIM` in a simulation), the handle is that display's marker and the addon **MAY** hide the display's strip. The tag meets every requirement of a marker above: it is text, localized, readable without hovering, and on the display in every layout the handle shows in. The strip comes back the moment the handle hides while placeholder data still draws: the display re-locked, or combat taking the handle down. An addon that keeps both, the strip stacked beyond the handle, stays compliant. Until v2.114.0 the handle's tag was lock chrome only and the strip showed beside it on every display.
  - **In a simulation the step panel stays.** A HUD display drawing simulated data carries the cyan strip, and the step panel stays on screen as well (*The in-game simulator*, below).

  This reverses v2.93.0's owner ruling of 2026-10-30, under which a HUD display **MAY** go unmarked in test mode and **MUST NOT** carry a simulation marker: on 2026-11-15 the owner ruled that a HUD shows the strip too, and that every window's strip sits under its title bar. **Adoption is blocked until `LibKa0s v1.103.0` is tagged**, because the docking ships there. Until an addon vendors that tag, a strip anchored between a filter bar and a body, an unmarked HUD display and a window that marks test mode with a title badge are re-vendor items rather than findings, graded as v2.109.0 read, and a strip the host already places where this paragraph puts it, a test or sim strip on a HUD display's top edge included, is **compliant** until then and does not have to move to the docking to stay so (anti-pattern #97 does not grade it; v2.112.2); from its re-vendor of the tag the addon owes this paragraph whole. A window or HUD display that draws test or simulated data with no strip is anti-pattern #97, except a HUD display whose drag handle shows carrying the mode's tag (v2.114.0); a strip placed anywhere but where this paragraph puts it, or anchored by hand, is anti-pattern #118.
- **The launcher's right-click menu drives this same switch** — its *Test mode* entry where the addon has a test mode, its *Locked* entry where unlocking is the preview — through the addon's own handler, the one the `test` / `lock` / `unlock` verbs and the Master-controls checkbox use, never a copy of the state; both entries are grayed while the addon is disabled (launcher-§2). The launcher's left-click opens the settings panel and drives neither; until v2.67.0 it drove this switch in an addon with no primary window.
- **The skin picker enters this mode (skinning-§10).** While an adopted addon's skin picker is up over a hidden display, the display shows in its test mode, or in its unlocked view under the exception above; the picker's eye toggles it through the same handler, and every close of the picker puts the mode back as the picker found it.
- **SHOULD** feed the preview through the **same render path** as live data (placeholder values in, real widget out) so it exercises the real layout, not a separate mock.
- **MUST** clear the preview and return to live data when the preview verb is toggled off, and, where unlocking *is* the preview (the exception above), when the display is re-locked. A **test mode** is not cleared by re-locking — it ends only by its own switch, by combat start, or by *Reset all settings*.
- Utility addons with no positionable display: **N/A**.

### The in-game simulator (MAY)

An addon **MAY** ship an in-game simulator: a session that plays scripted events through the addon's real engine, so a player can watch it work without a group, an instance or a real event. It is not a test mode. A test mode draws placeholder data on a display; a simulator feeds the engine, and the displays draw whatever the engine makes of it.

A described reference implementation: the simulator wraps the addon's `NS.Compat` table once, in a setup file loaded straight after the compat family (`Sim:NewSeam(compat, opts)`); binds one session to that seam with a descriptor of scenarios, a `deliver` into the addon's own event handlers and a `prepare` that builds its world (`Sim:New(d)`); and is driven by one feature-verb row, `/<slash> sim …`, whose words reach `sim:RunVerb`. The library's docked step panel shows the scenario's steps while it runs. From `LibKa0s v1.76.0` a session started from the verb or the panel plays on its own at the host's step delay. Pause holds it, and a step typed or a row clicked while it plays holds it first and then plays by hand.

An addon that ships one:

- **MUST** build it on **`LibKa0s-Sim-1.0`** when the simulator is first shipped on `LibKa0s v1.75.0` or later (library-stack-§7). Adoption is otherwise required of none: a simulator a host wrote before v1.75.0 is not anti-pattern #47 until the host adopts the major, and once it has, a private session, seam, timeline or step panel beside the major is #47.
- **MUST** route every client read the simulation answers, and every outward action, through its `NS.Compat` table (compat), because that table is what the seam wraps. Each is a `Compat` member read at call time. The seam is installed right after the compat family loads; a member captured in a local before then, or at any time (`local x = Compat.Member`), is the live one and answers live data during a session, silently.
- **MUST** refuse to start, on every surface alike, so a refused tick of the *Sim mode* checkbox leaves it unticked:
  - while the addon is stood down, with the line by hold (slash-commands-§7, *Which refusal, by hold*, the **SHOULD** it is there);
  - while test mode is on;
  - in combat, in an instance, or in a group.

  The host supplies every one of these through its descriptor's `refusal`, which the major runs inside `seam:Live`, so it reads the real world. The major adds no world rule and relaxes none. What it computes itself is the order (an unknown scenario, then a session already running, then the host's `refusal`) and a backstop that refuses while the descriptor's `isStoodDown` answers true.
- **MUST NOT**:
  - send anything: every outward member (chat, whisper, addon message, trade) is in the host's guarded set (`opts.guarded`), which the seam answers in place of the client while a session runs;
  - act on a real player;
  - write SavedVariables from a simulated event. The step panel's position is session-only. A session log the host keeps in memory and drops at stop is not SavedVariables.
- **MUST** leave the addon exactly as it was at stop. Every module the session touched registers its cleanup (`sim:OnStopGuarded` for a step that must still see simulated answers, `sim:OnStop` once the seam is off), and every timer inside the simulation is `sim:After`, so it dies with the session.
- **MUST** mark the session on screen while it runs, and the major's step panel is that mark (v2.93.0, owner ruling of 2026-10-30). The panel stays on screen for the whole session: a host whose session no window strip marks builds it with no close mark (`close = false` on its panel descriptor), so nothing the player clicks leaves a running session unmarked. Every window and every HUD display drawing simulated data also carries the strip's simulation flavor (`kind = "sim"`, Widgets minor 14, `LibKa0s v1.76.0`), placed as *Where the strip sits* says and under the same one-marker rule (**MUST** from the addon's re-vendor of `LibKa0s v1.103.0`, v2.110.0; before it a window **SHOULD** carry it and a HUD display carries none, as v2.93.0 read). The strip does not replace the step panel, which stays on screen for the whole session.
- **MUST** show the step panel on **every start** of a session (v2.120.0, owner ruling of 2026-11-24). The owner, 2026-11-24, after `/lh sim start loot` played Loot History's scenario with no panel: "sim mode whether started from a command like /xx sim start <scenario> or from just plain /xx sim should always show the sim stepper window (make this an upstream standards change)". Every route that starts a session shows the panel as the session starts: a bare `/<slash> sim`, `/<slash> sim start <scenario>` and any other verb that starts one, the panel's own Start row, the launcher's *Sim mode* entry, the Master-controls *Sim mode* checkbox (options-ui-§15) and a host's own start call. A session a suite starts headless, with no client to draw a panel in, is the one exception.
  - **On the major it is the library's (from `LibKa0s v1.113.0`).** Up to `LibKa0s v1.112.0` the grammar showed the panel on a bare `/<slash> sim` only (`SimTimeline.lua`'s `runVerb`), so `start`, and every other start path, played with the panel hidden; from `LibKa0s v1.113.0` the session's start shows it, whichever route called it. A host on the major passes nothing for it and never hides the panel on a start; a host that hides it after a start, or opens a session around the major's start, is this rule's finding.
  - **By hand otherwise, on any tag.** An addon whose simulator does not run on `LibKa0s-Sim-1.0` (one written before `LibKa0s v1.75.0`, above) shows its own panel on every start route the same way.
  - **When it binds.** An addon on the major owes it at its re-vendor of `LibKa0s v1.113.0`; before it a start route that leaves the panel hidden is a re-vendor item, not a finding. A start that leaves the panel hidden after that is **anti-pattern #126**.
- Has **three surfaces onto one handler, and no key binding** (v2.99.0, owner ruling of 2026-11-04): the `/<slash> sim …` feature verb, which the dispatcher refuses while the addon is disabled; the launcher's *Sim mode* entry (launcher-§2, Launcher minor 7); and the **`Sim mode` checkbox in General → Master controls**, next to *Test mode* (options-ui-§15). Ticking the checkbox does what the bare `/<slash> sim` and the launcher's `toggleSim` do (it opens the step panel, the sim window), unticking it stops a running session and hides the step panel, and it shows the live state: ticked while the step panel is shown or a session is running, unticked when neither (v2.100.0), so a window opened or closed and a session started or ended anywhere else ticks or clears it. It is session state and never persisted. The key binding stays *Show window*'s alone (launcher-§6). Until v2.99.0 this bullet called the simulator slash-only with no launcher entry; launcher-§2 added the entry in the full skinning run, and the checkbox follows it. A simulator with no Master-controls checkbox is **anti-pattern #112**.
- Keeps its host members off the library instance. The host holds its own table for its own fields, and a running session's host fields go on the session table (`sim:Session()`).
- Asserts in its own suite that `seam:Unwrapped()` is empty after the whole addon loads: a `Compat` member added after the seam, or replaced by assignment, escapes it.

These are the host's contract. The library guarantees only what it computes, the refusal order with its stood-down backstop and a guarded member that never reaches the client while a session runs, and never advertises the rest as enforced (`LibKa0s#54`). The full descriptor and its obligations are in the `LibKa0s-Sim-1.0` API document (`docs/api/Sim/` in the library repo).

### Sample characters (MUST at adoption, v2.113.0, owner ruling Q4 of 2026-11-16)

A test mode, a simulator and a showcase all draw made-up people, and before this rule the collection used five conventions for them: `Sample`/`Mock` names, `Test` names, fantasy lists, real realm names and a localized name (LibKa0s#87). A sample that looks real reads as a real player's data, and a real realm or a real-looking `Name-Realm` pair can be one. The owner ruled on 2026-11-16 that **this standard owns the naming convention and `LibKa0s-Sim-1.0` owns the data**. These rules mirror the convention recorded in the Sim major's API document (Sim minor 3, `LibKa0s v1.105.0`, `docs/api/Sim/version-3.3.11.4-docs.md` in the library repo; rule 6 as `LibKa0s v1.113.0`'s Sim document restates it), whose suite holds the library's data to them case by case:

1. **Obviously fictional.** A character name, a surname and a pet name is one capitalized word of 2 to 12 letters, a name the client could hold, that **starts `Sample` or `Mock`** (`Samplehunter`, `Mockflame`, `Mockfang`). A guild follows the same pattern (`Sample Company`, `Mock Brigade`).
2. **Fixed fictional realms.** `Samplerealm`, and `Mockrealm` for a character from another realm. **Never a real realm name**, so never a real-looking `Name-Realm` pair, and never a real player's name.
3. **The client's identity shape** (clients; client-quirks-§5, forever-quirks-§4). Retail: `Name-Realm`, with a `specID` that is one of the class's own. WoW Forever: `First Surname`, with **no realm in the identity**, a class the client has, and a classic talent tree (1 to 3, in `LibKa0s-Role-1.0`'s `TALENT_GROUP_ROLE` order) in place of a spec ID.
4. **A pet only on a class that has one** (Hunter, Warlock).
5. **Names are data, never localized**, and never pass through the addon's `L` table. A spec label in the data is English; a display that draws a spec name asks the client for its own.
6. **Every name comes from the library (v2.120.0).** Every named sample person an addon draws, in a test mode, a simulator, a preview or a showcase, protagonist or crowd, is the library's. The protagonists are `Sim.SAMPLE.retail` and `Sim.SAMPLE.forever` (the same five people on each client), read for the running client through **`Sim.Sample(client)`**, which answers a copy the caller owns. Every further person comes from the library's shared crowd, **`Sim.SampleCrowd`** (from `LibKa0s v1.113.0`, LibKa0s#104): deterministic, in the running client's identity shape, its exact signature and guarantees in the Sim major's API document. An addon that needs a seeded crowd seeds the library's, and keeps its determinism through the seed, never through a list. **No addon keeps a sample-name list of its own**, so no `Sample…` or `Mock…` person literal lives in its shipped code. Until v2.120.0 this rule read "The protagonists converge; roster pools do not" and let an addon keep its own crowd pool; the owner's request of 2026-11-24, "adopt the predefined test mode names consistently across all addon's test/sim modes", retired that (Ka0sAddonsCommonTasks `docs/2026-11-24-FEEDBACK_BATCH/R2_SMOKE_FEEDBACK.md`, decision D1, option (a) of LibKa0s#104).

An addon **MUST** follow rules 1 to 5 for every sample identity it ships (placeholder data, simulator scenarios, showcases and screenshots made from them), and **MUST** draw every named sample person from the library under rule 6, never from a copy of the library's rows. A load with the library absent draws no named sample person of the addon's own: its sample data degrades to unnamed rows, or to none. Rule 6 names people: a guild name the library's rows do not carry stays the addon's data, under rules 1 to 5. A test fixture under `tests/` is not shipped data, but a fixture that pairs a real-looking name with a real realm **SHOULD** move to the convention at the same time, and the addon's suite **SHOULD** assert that no `Sample…`/`Mock…` person literal lives outside `tests/`. **When it binds:** rules 1 to 5 bind when the addon adopts the sample data, tracked by LibKa0s#87 (library-stack-§7, *What a re-vendor owes and what adoption owes*); a re-vendor to `LibKa0s v1.105.0` alone owes nothing under them, and an addon's existing samples are not graded until that adoption. Rule 6 binds at the addon's re-vendor of `LibKa0s v1.113.0`, tracked by LibKa0s#104; before it a list of the addon's own is a re-vendor item, not a finding, and after it a list of its own is **anti-pattern #128**. A new addon's samples follow both from the first commit. The release re-look below (*Kept current at every release*) checks the samples like any other placeholder data once the addon has adopted.

### Kept current at every release (MUST)

This applies to every addon that ships a test mode, a preview drawn by unlocking, or a simulator. A frameless addon, with no positionable display and no simulator, owes only the *Not applicable* answer below.

At every version bump (versioning-git) the addon **MUST** re-look at its placeholder data, its simulator scenarios and the suites that cover them, on three counts:

- **Coverage.** Every display element and feature the release adds or changes that the preview draws appears in the placeholder data. Every event-driven feature added since the previous release that a scenario could exercise is in a scenario step, or the scenario list says why it is not.
- **Currency.** Data naming game content (item, spell, encounter, instance, currency and affix ids or names, the season's dungeon list, level and item-level ranges) matches the season and patch the release targets, which the TOC `## Interface:` names (toc-file-§3).
- **Fidelity.** The data and the scenarios still drive the current render path, verbs and UI: no field the display stopped reading, no removed option, and no step driving a control that is gone.

The addon **MUST** record the outcome in that release run's `ANALYSIS.md`, under `## Preview and simulation data` (automated-tests-§5), with exactly one answer:

- **Current**: nothing needed changing.
- **Refreshed**: the data or scenarios were brought up to date, citing the commits.
- **Deferred**: the re-look found work that did not land in this release, naming the reason; it **SHOULD** cite a GitHub issue.
- **Not applicable**: the addon is frameless, as above.

The section also lists the files reviewed. `/dev-copilot:bump-version` asks the question before its release gate and writes the section; a release recorded by hand asks the owner the same question.

Why at release: data naming game content ages with every patch, and nothing else revisits it. The measured shape: the test-mode strip and the simulator arrived in v2.86.0, and their data and scenarios have no other checkpoint.

The rule commences with each addon's first release after v2.87.0. Release bundles frozen earlier are not backfilled (automated-tests-§5). It carries no anti-pattern number: a missing section, or one without an answer, is a **MUST** finding against preview-mode.
