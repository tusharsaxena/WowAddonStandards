> Part of the **[Ka0s WoW Addon Standard](../STANDARDS.md)** — the split standard. Cross-references use the `filename-§N` form (see the index's section map).

## Skinning: one skin per addon, through the library's facade

A **skin** is a named look for every visual element an addon draws: its windows, panels and dialogs, list rows, the tooltips and menus it owns, its settings pages, the library tool windows it hosts (debug console, perf and sim panels, copy windows), test strips, charts and its HUD. The player picks the skin **per addon**, in a **Skin** tab on the addon's General page. The collection ships nine skins, and the first of them, **Ka0s Default**, is the Ka0s look every Ka0s addon drew before skins existed; the client's own stock look is a skin too, **WoW Default**. Instead of a Ka0s skin the player **MAY** take the addon's look from **EllesmereUI**, when that suite is loaded and its third-party skinning is on for the addon.

All of it is drawn by `LibKa0s-Skin-1.0` (from `LibKa0s v1.78.0`). A skin is **data**, a token table inside the library, and the painting vocabulary mirrors EllesmereUI's skinning API by name (`Shell`, `Panel`, `Button`, `EditBox`, `Checkbox`, `ScrollBar`, `Tab`, `CloseButton`, `Font`, `GetAccentColor`, `OnLooksChanged`, ...) so that a call site reads the same under either provider. The names and the token model are mirrored; EllesmereUI's code and media are not, because its license reserves all rights (library-stack-§6).

### 1. Adoption and the owner (MUST)

**An addon has adopted skins when its own code calls `Skin:RegisterOwner(<its folder>)`.** That one call is the test, mechanically: `grep -rn 'RegisterOwner(' --include='*.lua' core modules settings` returns it or it does not. Everything below binds an addon from its adoption (§8); an addon that has not adopted is graded against the rules §7 lists exactly as they read for it, and nothing in this section is a finding against it.

- **The owner is the addon's FOLDER name**, the first vararg of the file that registers it, for the reason library-stack-§8 gives for every path the library builds: nothing else the addon carries *is* that string, and a near miss (an `## Title`, a frame-name prefix, the brand) registers an owner nothing else asks for. The same string is what `LibKa0s-Options-1.0`'s descriptor already carries as `addonName` (options-ui-§1), so a page's owner and the addon's owner are one name.
- **Register once, at file load, in one setup file.** The call sits in its own setup file, `core/SkinSetup.lua` by convention, matching library-stack-§7's one-file-per-module pattern, with a degradation stub beside it. It runs at **file load**, never at `PLAYER_LOGIN`, because the EllesmereUI provider has to offer the owner to EllesmereUI before EllesmereUI dispatches its skins (§5). `opts.get` answers the stored choice and `opts.set` writes it through the addon's write seam (§2); `opts.label` is the brand the Skin tab and the copy confirmation print.
- **Every visual element of an adopted addon paints through the facade.** `Skin:For(owner)` returns the owner's facade, `S`. Addon code calls a primitive once, at frame creation (`S.Shell(frame)`, `S.Button(btn)`, `S.Text(fs, role)`), and the library records the frame against the owner so that a skin change repaints it with no further call. Colors, fonts, textures, borders and backgrounds that the addon would otherwise write itself are read from the skin (`S.Color(name)`, `S.Token(name)`), never typed at the call site (anti-pattern #107).
- **Every surface follows the skin, and the kit enforces it.** From `LibKa0s v1.85.0` a surface a skin can reach reads a token and a typed value needs a named allow cause (§9). The re-vendor adds two kit suites, declared by the pair like any kit suite (testing-§9), `{ name = "test_skin_values", dir = "tests/_kit/" }` and `{ name = "test_skin_switch", dir = "tests/_kit/" }`, and an adopted addon wires both: `Kit.skinValues` for the typed-value gate and `Kit.skinSwitch` for the switch test, each set in `tests/run.lua` before `Kit.run`. Declared with no facts, each is one skip that names this section, which keeps the re-vendor commit green and is not adoption. `test_skin_literals.lua`, the copy eight addons carried, is deleted or keeps only the cases that are not the gate. The library's `docs/api/testkit` document for revision 50 is the adoption route.
- **The addon's own colors are owner tokens.** A color the addon draws that no library token describes, whether a near miss of one (a gray a few levels off `text.muted`) or a meaning of the addon's own (an upgrade, a pace lead), is declared once as an **owner token** in the `tokens` table of `Skin:RegisterOwner(owner, opts)` and read through the facade like any library token (`S.Color("dw.upgrade")`). It is never typed at a call site, and never snapped to the nearest library token, which would move a Ka0s Default pixel (§4). Each entry carries:
  - a **name** in the addon's own namespace, a short prefix and a dot (`dw.upgrade`, `dr.ahead`), never a library family (`text.`, `sem.`, `gtip.`, ...) and never a schema path; the library refuses, and logs, a declaration outside the owner's namespace or one that collides with a name already taken;
  - a **`default`**, the Ka0s Default value, which is the color the addon drew before it adopted, exactly;
  - a **`follow`**, the nearest library **role** token (a gain follows `sem.good`, a note gray `text.muted`, a tooltip hint `gtip.muted`), whose value the owner token takes in every other skin and under EllesmereUI, so each skin draws it in its own palette;
  - optionally **`skins`**, a value of its own for a named skin where the follow token's would read wrong.

  An owner token is not a skin and patches none: it adds a name the owner reads and changes no library token in any skin, so §4's ban stands. A color several addons share belongs in the library as a library token, added upstream in a library minor (§4).
- **A box or button that needs other tokens names them.** `Shell`, `Panel`, `Card`, `Inset` and `Button` take `opts.tokens`, a table from the primitive's slots (`bg`, `border`, `text`, `hover`, ...) to library or owner token **names**, in place of the primitive's fixed spec: a danger button, a caution callout, an opaque modal, an alternate card fill. It takes names, never values; a color value in `opts.tokens`, or a primitive's paint overwritten after the call, is anti-pattern #107.
- **The stock look is a skin, never a host switch.** Ka0s Default paints the Ka0s look on every frame an adopted addon draws, a window built on one of the client's templates included; a player who wants the client's stock look picks the **WoW Default** skin (§4), and a player who wants the settings panel or the fonts left alone says so in the Skin tab's Scope (§3). `opts.stockDefault`, which `LibKa0s v1.80.0` offered so that a window built to match Blizzard's settings window kept its stock art under Ka0s Default, is **retired** in `LibKa0s v1.81.0` (owner ruling of 2026-10-30): the library ignores the key without an error, so an addon a release behind degrades to the Ka0s look, and an adopted addon **MUST NOT** pass it from its re-vendor of that tag. `opts.stock` is not a stock look and stays: it lists template art a primitive fades, and it is honored under every skin.
- **Owner tokens and `opts.tokens` ship in `LibKa0s v1.80.0`** and bind an adopted addon from its re-vendor of that tag.
- **Every library factory that takes an owner is given one.** `Core.ApplySkin`, `MakeCloseButton`, the `LibKa0s-Widgets-1.0` factories (dropdown and its shared menu, search box, copy window, test strip, autocomplete, drag handle, reorder list, line chart), the tool windows' descriptors and the Options descriptor's `addonName` each accept the owner, additively. Called without one, or with a name that is not a registered owner, each draws Ka0s Default exactly as it did before skins, so an addon that has not adopted is unaffected by a re-vendor.
- **Every custom library widget is skinned and obeys the Scope.** From `LibKa0s v1.81.0` every widget the library draws for an owner, not only the AceGUI rows (the `LibKa0s-Widgets-1.0` controls above, the tool windows and the window grip, the Options chrome, the tooltip lines the library writes), paints from the owner's skin tokens and obeys the Skin tab's Scope exactly as §3 defines it (owner ruling of 2026-10-30). A widget that is used both on a settings page and in a window cannot know where it is, so the host says so: `S.Text(fs, role, { panel = true })`, and the `panel` flag every owned Widgets constructor takes, for one placed on a settings page; the reorder list, which every consumer puts on a settings page, is panel-scoped by default and takes an opt-out. A host that paints a settings-page surface of its own from tokens gates it on the public `Skin:GetIgnore(owner)`, never an internal of the library, so one page never mixes stock and skinned.
- **Facade overlays follow frame-layering-§3.** A primitive that adds art (a border, a title-bar fill, a divider, a list-row stripe) draws it on a holder child frame one level over the frame it decorates, created once per frame and reused on every repaint, and never as a direct region of a frame another provider may fade. The holder is part of the element's band, so the order fill < border < overlay holds under every skin.
- **Shared objects follow whoever opened them.** The library's one popup menu, the reorder ghost and any other library singleton are repainted on **every** open: to the opener's skin when the opener is a registered owner, otherwise back to Ka0s Default. A singleton left in the last owner's colors is a leak across addons (§7).

### 2. The choice is per addon, per profile (MUST)

The skin choice is **two values**: the **source**, `ka0s` (a Ka0s skin) or `eui` (EllesmereUI), and the **skin**, one of §4's keys. Both default to `ka0s`.

- **Per addon.** Two addons sharing one loaded copy of the library show two different skins at once. There is no collection-wide skin and no account-wide store for one; the Skin tab's *Copy to every Ka0s addon…* (§3) is the way to make several addons match, and it writes each one's own choice.
- **Per profile, through the write seam.** The two values are stored in the profile, written **only** through the addon's single write seam (options-ui-§1) — the function `opts.set` names and the tab calls. Where they live inside the profile is the addon's own convention (`appearance.source` and `appearance.skin` are the shape the first adopter uses); they are defaulted by AceDB like any other profile value.
- **A profile change re-applies the choice.** A profile switch, copy or reset hands the new values to `Skin:SetChoice(owner, source, skin)`, which repaints the owner's frames. `SetChoice` is idempotent, so a write that reaches it twice (the tab, then the row's own `onChange`) repaints once.
- **Ka0s skins switch live.** A change between two Ka0s skins, and a change from `ka0s` to `eui`, repaints every recorded frame of that owner and nobody else's, with no reload, no `OnUpdate` and no event. A change **away** from `eui` cannot (EllesmereUI's paint is one-way, §5): it offers a reload instead, once, and never claims to have repainted.
- **Settings rows repaint by re-rendering.** AceGUI rows on an open page are not repainted in place: the page re-renders on the next frame, which releases each widget (restoring it, §7) and acquires it again under the new skin.

### 3. The Skin tab (MUST, for an addon that has adopted skins)

- **Where.** A tab on the **General** page labeled exactly **`Skin`** (its key, which a host names in `before` and in a stored active tab, stays `Appearance`), immediately **before** `Keybindings`, or **last** where the page has no Keybindings tab. `Master controls` stays first (options-ui-§15) and `Keybindings` stays last (options-ui-§20). On a page drawn by `O.RenderTabbedSchema` it is a host tab in `opts.tabs` whose `before` is the Keybindings tab's key; on a General page the host draws itself, it is the strip entry before Keybindings, with its body drawn through `O.AppearanceRows(ctx, spec, parent)`. The tab counts toward options-ui-§13's budget of eight tab labels per page (six beside a nav rail); a General page already at the budget merges a tab rather than wrapping the strip for this one.
- **Drawn by the library.** `O.AppearanceTab(spec)` (`LibKa0s-Options-1.0`, from `LibKa0s v1.78.0`; labeled `Skin` since `LibKa0s v1.79.0`) returns the tab entry; `spec.get` and `spec.set` are the owner's read and its write seam (§2), and `spec.strings` translates, and only translates, every string the tab draws, the skins' names and descriptions included. A hand-built skin picker beside it is **anti-pattern #47**.
- **What it holds.** The **skin source** (Ka0s skins, or EllesmereUI, the latter disabled with a hint while §5's gate is closed, each condition listed with a check or a cross and its one-line fix); the **skin**, a choice grid of the nine with each one's swatches, name and one-line description, where selecting one repaints live; the owner's **font and texture** overrides, each a preview picker (options-ui-§23) whose first row is ***Skin's default (X)***, X naming what the skin draws (the wording from `LibKa0s v1.83.0`, owner ruling of 2026-10-31), with a row of two half-width buttons under the pickers, **Reset font** and **Reset texture**, each putting its override back on the skin's default and disabled while it already is (from `LibKa0s v1.82.0`; no confirmation, so no ellipsis, options-ui-§21); the **Scope**, two check boxes, *Ignore settings panel* and *Ignore fonts*, and the ***Font outline*** choice (below); **Copy to every Ka0s addon…**, under a heading of its own, *Other Ka0s addons*, which carries the source, the skin, the Scope, the font outline and the overrides (options-ui-§21's ellipsis: it opens a confirmation naming the loaded addons it will change and saying that addons not loaded are unchanged; disabled, with a hint, while no other loaded addon has adopted); and the library's fixed note that a skin changes every visual element and that HUD style options follow the skin unless the player sets them.
- **The Scope means exactly this.** The two check boxes are the player's exceptions, per addon and per profile, stored through the write seam like the choice (§2) and applied through `Skin:SetIgnore`; a host reads them through `Skin:GetIgnore(owner)`.
  - ***Ignore settings panel*** covers the addon's **settings panel and nothing else**: its AceGUI pages, the Options chrome (drawer, nav rail, tab strips, id lists, this tab itself) and any library widget the host places on a settings page (§1). While it is on, all of them keep the client's look under every skin. Windows are not the settings panel: the debug console, copy window, perf and sim panels, drag strips, the first-run skin picker and the addon's own editors, browsers and modals wear the skin whatever this box says. It **defaults to on** in every profile (owner ruling of 2026-10-30).
  - ***Ignore fonts*** reaches **every string the library paints for the owner**, windows and the HUD included (§6), except the first-run picker's skin rows, which preview each skin's own face because they exist to show the skins, and a media picker's font rows, which draw each entry in its own face for the same reason (options-ui-§23): each string keeps the face and size it was given, and the skin still colors it. It defaults to off.
- **A skin change resets the overrides (MUST, owner ruling of 2026-10-30, from `LibKa0s v1.82.0`).** When the player chooses another skin and the look the owner draws changes (`Skin:DrawsKey(owner)` read before against after), the font and texture overrides go back to the new skin's default in the same write. Every choice the player makes goes through the library's one chooser, `lib.__chooseSkin` (a documented internal of `LibKa0s-Options-1.0`): the tab's grid, the first-run picker (a preview clears the overrides on screen, closing restores them, *Apply* saves them cleared) and the picker's *Apply to all*. It never happens inside `Skin:SetChoice`, which runs at login and on every profile change and applies the stored values as they are. *Copy to every Ka0s addon…* carries this owner's overrides to its targets and resets nothing, and `/<slash> set` on the stored skin path stays a raw write that resets nothing. The *Font outline*, the Scope and the HUD style values the player set (§6) are not overrides and survive a skin change.
- ***Font outline* (MUST, owner ruling of 2026-10-30, from `LibKa0s v1.82.0`).** A dropdown with three values, *All text*, *HUD text only* (the default from `LibKa0s v1.83.0`, owner ruling of 2026-10-31; *All text* was the default in `v1.82.0`) and *Off*, stored per profile at `skin.outline` (`all`, `hud`, `off`) through the write seam like the Scope, and applied by the Skin major. The default reaches an owner that never set one, a stored choice stays, and an addon's profile defaults that stored `all` move to `hud` on the re-vendor. It decides where the skin's outline flag applies. The flag is the skin's `hud.outline`, `OUTLINE` in every shipped skin, and `OUTLINE` where a skin states none: under *All text* both `font.outline` and `hud.outline` answer it, so every string the library paints for the owner is outlined; under *HUD text only* `font.outline` answers `""` and `hud.outline` the flag; under *Off* both answer `""`. It never outlines the monospace role (the debug console and every glyph drawn in the mono face, debug-logging-§2). *Ignore fonts* wins: while it is on, the choice is not read and the library adds no outline of its own (`font.outline` answers `""`, `hud.outline` as §6 says), so a *From skin* flag resolves to none and only a flag the player picked applies; the dropdown is grayed, and its tooltip says why (options-ui-§21, *Dependent rows*). A HUD element's own *Font flags* row follows it through its *From skin* value (§6, options-ui-§16).
- **The skin picker, and `/<slash> skin` (MUST).** An adopted addon shows the library's first-run skin picker (`O.SkinPicker`, `LibKa0s-Options-1.0`) once per profile, on a profile that has not seen it (owner ruling O3 of 2026-10-29), and again whenever the player types **`/<slash> skin`** (slash-commands-§2, owner ruling of 2026-10-30). Under its skin list the picker offers the Skin tab's **font, texture, outline and scope** (owner request of 2026-10-31, from `LibKa0s v1.83.0`): *Font* and *Texture* as `Ka0sMedia_*` preview pickers (options-ui-§23), the *Font outline* choice, and the Scope's two check boxes. A change previews, *Apply* saves it through the write seam, closing puts it back, and *Apply to all* carries all four with the skin. The verb's act is the library's `O.SkinVerb(spec)` (OptionsSkinPicker minor 3, `LibKa0s v1.82.0`), handed the host's own first-run spec: it opens the same picker in the same state a new profile shows, whatever the profile's *picker seen* flag says, and writes nothing until the player applies. The row is the addon's own, in its `COMMANDS` table directly after `config`, calling `NS.RunSkinVerb()`. The verb takes no argument. In combat it shows nothing and prints the library's gray refusal on **every** call, not once per combat, because a typed command that answers nothing reads as broken; while the addon is disabled it **MUST** be refused with the disabled refusal line, by ruling, although it is a settings verb rather than a feature verb, and a host **MUST NOT** list it in its `liveVerbs` (slash-commands-§2, slash-commands-§7). A hand-built window for it is **anti-pattern #47**. While the picker is up, the addon's main surface shows in its preview mode, the eye toggles it, and every close puts back the state the picker opened with (§10).
- **Resets reach it as a profile value.** *Reset all settings* (options-ui-§12) resets the profile, so the choice returns to Ka0s Default and is re-applied (§2). The tab holds rows of its own, so it meets options-ui-§13's two-line floor.
- **Degradation.** The Options degradation stub answers `AppearanceTab` and `AppearanceRows` (options-ui-§1). `Kit.assertSurfaceParity` compares the stub against the live instance, so every addon's stub, adopted or not, owes the two members from its first re-vendor of `LibKa0s v1.78.0`, the same footing as options-ui-§20's three, and `SkinVerb` from its first re-vendor of `LibKa0s v1.82.0`. Without the library the tab is not drawn and the addon draws Ka0s Default's values through its own fallbacks.

### 4. The shipped skins

Nine skins ship in the library. The **key** is what the profile stores; the **name** is what the tab shows.

| key | name | in one line |
|---|---|---|
| `ka0s` | Ka0s Default | the collection's look before skins: slate, gold, Blizzard buttons |
| `obsidian` | Obsidian | flat and quiet, one blue accent |
| `azeroth` | Azeroth | parchment and leather, like a quest log |
| `glass` | Glass | translucent panels with rounded corners (the client draws no blur) |
| `contrast` | High Contrast | black, white and yellow, 2px edges |
| `ember` | Ember | charcoal and brass with a fire accent |
| `wow` | WoW Default | the vanilla client: stone, steel trim, red buttons with gold text |
| `midnight` | WoW Midnight | night blue, gold and violet |
| `forever` | WoW Forever | warm charcoal, black title bars with centered white titles, a tan accent, gold headings, thin borders |

- **Ka0s Default reproduces the Ka0s look as it was.** Its values are the ones the rules §7 lists state, and an addon that adopts skins and leaves the choice at its default draws exactly what it drew before; every golden and color pin it carried stays green unchanged. Two exceptions are owner rulings of 2026-10-30, recorded in `LibKa0s v1.81.0`'s changelog: a window that kept the client's stock art under Ka0s Default (§1's retired `opts.stockDefault`) now wears the Ka0s look, and a custom library widget skinned for the first time (§1) takes Ka0s Default's face and colors, its tooltip palette included, so a pin of a color the widget drew before (the client's yellow drawer chevron, now `icon.arrow`; white suggestion rows, now `menu.text`; the id gray, now `text.disabled`) moves. A third is owner ruling R-8 in the same changelog: the `q.*` tokens, formerly the client's quality colors rounded to two places, now equal the client's colors exactly, so a pin of the rounded values moves. A fourth and a fifth are owner rulings of 2026-10-28 and 2026-10-30, recorded in `LibKa0s v1.79.0`'s and `v1.82.0`'s changelogs: Ka0s Default's text face and bar texture are the skin's own, not the client's (Oxanium from `v1.79.0`, Ka0s Prototype from `v1.82.0`), and its text was outlined by default in `v1.82.0` (§3, *Font outline*), so a pin of the client face or the client bar under Ka0s Default moves; from `v1.83.0` the default outline is *HUD text only*, so a string that is not HUD text is unoutlined again, as it was before `v1.82.0`. A sixth is the owner's ruling of 2026-11-01 (§9, `LibKa0s v1.85.0`): a surface moved onto a skin primitive (a hand-built tab, column band, footer, row hover or icon edge, a window's title bar, a mark replaced by a tinted Ka0s icon) and a HUD color a migrated profile had stored now draw Ka0s Default's tokens, so a pin of the old look moves, and each move is named on that run's smoke list.
- **WoW Default is the stock look.** It is the skin for a player who wants the client's own look, and the only way an adopted addon offers that look on its windows and HUD; the settings panel's is the Scope's *Ignore settings panel* (§3). Its face is the library's `Ka0s Friz Quadrata TT`, never the client's file (*Fonts and art*, below).
- **A skin is library data (MUST NOT).** A skin is a token table registered inside `LibKa0s`. An addon **MUST NOT** register a skin of its own or patch one: the registry is process-global, so a local skin is offered to every addon on the client. A new or changed skin is a library minor, added upstream like a missing icon mark (library-stack-§8). An owner token (§1) is not a skin of the addon's own: it names a color under the owner's namespace and leaves every library token's value in every skin as it was.
- **Meaning colors keep their meaning.** Item quality, class colors, gain and loss and the test strip's amber and cyan mean the same thing under every skin. A skin **MAY** change their **legibility** (a darker quality color on a light background) through its semantic tokens; it never changes which hue means what. In an addon that has adopted skins, those colors are read from the skin's semantic tokens too, which under Ka0s Default answer the values the addon used before.
- **Fonts and art.** Skins name faces, borders and backgrounds by their LibSharedMedia keys, and the library resolves each at paint time, falling back to the client font where a face does not cover the client's locale (library-stack-§8). A skin never builds a file path. **Every skin names its own HUD face** (`hud.font`), so HUD text changes face with the skin as the rest of the addon does (owner ruling of 2026-10-30, from `LibKa0s v1.81.0`): each skin a face the library ships (library-stack-§8, *The skin media*, under the terms recorded there). WoW Default draws `Ka0s Friz Quadrata TT` from `LibKa0s v1.83.0`, not the client's Friz keys, because what those draw depends on the client's file: on the owner's client `Fonts/FRIZQT__.TTF` is byte-identical to Ka0s Prototype, so Ka0s Default and WoW Default set the same text. **Which face a skin draws is library data**, set in the library's skin table: from `LibKa0s v1.82.0` (owner rulings of 2026-10-30) Ka0s Default draws Ka0s Prototype for body, titles and HUD, Obsidian Ka0s Expressway for body, titles and HUD (it ships on the owner's ruling, library-stack-§8), and WoW Forever Ka0s Fira Sans Medium for body with Ka0s Fira Sans SemiBold for titles and HUD, the other skins keeping their faces. From `LibKa0s v1.83.0` (owner rulings of 2026-10-31), for body, titles and HUD, WoW Midnight draws Ka0s Segoe UI Semibold with Ka0s Segoe UI Bold for titles, Azeroth Ka0s Open Sans Semibold with Ka0s Open Sans Bold for titles, Ember Ka0s Emblem, High Contrast Ka0s Doris PP and Glass Ka0s Avant Garde. Those last three and WoW Default have one weight, so a title is the same face set larger. A face no skin names stays in the payload (library-stack-§8).
- **Geometry is skin-invariant.** Title-bar height, scrollbar width and every content inset are Ka0s Default's in every skin, and border art is drawn outside, or inside a fixed inset, so no skin moves a content anchor. options-ui-§8's layout constants hold under every skin.
- **Text width is skin-invariant (MUST, owner ruling of 2026-10-30, from `LibKa0s v1.82.0`).** Every layout in the collection is built for Ka0s Default, so every other skin's default sizes (`font.bodySize`, `font.titleSize`) are chosen so that its faces set a reference string about as wide as Ka0s Default's faces set it (Ka0s Prototype at 12 and 14), never visibly wider: a string that fits under Ka0s Default fits under every shipped skin. The sizes are measured on the shipped bytes **with the outline on**, the widest text the *Font outline* choice can ask for (§3), from each face's advance widths over a fixed reference corpus, and the library's suite asserts the recorded ratios, so a face or size change that breaks parity fails a test rather than a layout. The tolerance is the library's: the ratios and the band its suite (`tests/test_skin_width_parity.lua`) asserts at the tag that ships them, the band restated in that tag's Skin API document, are the normative values, and an auditor grades a skin against them, never by eye. HUD text scales the same way: each skin carries a HUD size factor (`HUD_SIZE`), and an element drawing the skin's face sizes its text through **`S.HudFontSize(size)`**, which scales the stored size at paint time and never rewrites it (owner ruling of 2026-10-30). From `LibKa0s v1.83.0` WoW Default is held to the same parity, measured on the Friz Quadrata it now ships, and every face change keeps it (owner ruling of 2026-10-31). A fixed-width label the library draws (a drag strip's title, a strip, a button) fits its text under every shipped skin, re-measured in its own font on every skin repaint, or the library widens it; it never truncates it. An addon's own fixed widths are held to the same test under Ka0s Default.
- **A font override scales the same way (MUST, owner ruling of 2026-10-31, from `LibKa0s v1.83.0`).** The library carries a per-face width table for every face it ships, measured like the skins' sizes against Ka0s Prototype, so a Skin-tab font override that picks a Ka0s face is scaled to Prototype's width rather than set at the skin's size for a different face. A face another addon registered with LibSharedMedia cannot be measured in the client and stays unscaled. A HUD element's own face pick keeps its stored size (§6). The sizes are the library's, `lib.__FACE_SIZES` in `SkinDefs.lua`, each row held to the skins' band by the same suite.
- **An enabled control reads as enabled in every skin (MUST, owner ruling of 2026-10-30, from `LibKa0s v1.82.0`).** A button's label keeps a contrast against its own fill that reads as live, an accent (primary) button's above all, in every shipped skin; the dim, low-contrast label is the disabled state's alone. The library's suite guards each skin's label-to-fill contrast for every button kind it paints, so a skin whose accent label reads as grayed fails a test, not a smoke pass. The threshold is the library's: the minimum label-to-fill contrast ratio its guard asserts, recorded in the library's changelog for the tag that ships it, is the normative value.
- **WoW Forever is a look.** It is the EllesmereUI-on-WoW-Forever appearance, usable on retail. The WoW Forever client itself is not supported (open-evolutions).

### 5. The EllesmereUI provider (MUST)

With the source set to `eui`, the library hands each primitive call to EllesmereUI's own facade for the names EllesmereUI has, and paints the Ka0s extras (title bars, dividers, list rows, cards, strips) from EllesmereUI's accent, panel color and font.

- **The gate.** The source is selectable only while all four hold, each read at call time: `EllesmereUI.RegisterSkin` is a function and `EllesmereUIBlizzardSkin` is loaded; `EllesmereUIDB.thirdPartySkinsOff` is not truthy; `EllesmereUIDB.thirdPartySkinAddons[<owner>]` is not `false`; and EllesmereUI handed the owner its facade this session. While the gate is closed and EllesmereUI has not painted this session, the owner falls back live to its Ka0s skin and the Skin tab says which condition failed.
- **The read is library-stack-§6's skinning exception.** The two `EllesmereUIDB` reads above are the one named exception to library-stack-§6's ban on reading a suite's SavedVariables: confined to `LibKa0s/SkinEUI.lua`, read-only, at call time, nil-guarded, never written. An addon **MUST NOT** read `EllesmereUIDB` itself, and **MUST NOT** copy the gate: it asks the library (`Skin:GetEUIStatus(owner)`). An addon that read `EllesmereUIDB` under a ratified register row before the provider existed keeps that row until it moves onto the provider.
- **`## OptionalDeps`.** An adopted addon lists `EllesmereUI` in `## OptionalDeps:` (library-stack-§6(b)), never in `## Dependencies:`, so that EllesmereUI loads first where it is installed and the addon is offered in its Third-Party list.
- **One-way, and said so.** `ka0s` to `eui` applies live. `eui` to anything else, or a gate condition failing after EllesmereUI has painted this session, offers **one** reload and never falls back live, because EllesmereUI's paint cannot be removed without one.
- **Fail closed.** A facade missing a primitive the provider needs is refused before any paint, latched and logged once; a paint that raises leaves the frame as it was. Pooled and shared objects (AceGUI widgets and pull-outs, the library's popup menu and reorder ghost) are **never** handed to an EllesmereUI primitive: under `eui` they keep the library's own technique, colored from EllesmereUI's getters, because EllesmereUI's paint is one-way and a pooled frame would carry it into another addon.

### 6. HUD style follows the skin (MUST, owner rulings R3 and of 2026-11-01)

A skin reaches the HUD too: bars, icons, glows and HUD text. A HUD style setting (a bar texture, a border, a HUD font and, from `LibKa0s v1.85.0`, a HUD color or shadow) of an adopted addon **follows the skin** unless the player has turned that off.

- **Through the library's seam.** A stored value resolves through `S.Resolve(kind, value)`, which answers the skin's value for the sentinel `Skin.FROM_SKIN`; a font, border or bar group composed by `LibKa0s-OptionsCompose` takes the composer's `fromSkin` companion row (*Use the skin's font*, and so on), which disables the picker while it is on (options-ui-§16). A sentinel string never enters a LibSharedMedia list or the CLI's allowed values.
- **Reset once, on adoption.** Under the collection owner's ruling R3, the chosen skin shows **at once**: the addon's adoption resets the player's saved HUD style values to follow the skin, **once**, as one per-profile step in its own migration runner (savedvariables), through `Skin.ResetToSkin` or by setting the companions. A player who then sets a value keeps it.
- **HUD colors follow the skin (MUST, owner ruling of 2026-11-01, from `LibKa0s v1.85.0`).** HUD colors were the player's: the rollout's decision X4 (Ka0sAddonsCommonTasks `docs/2026-10-29-SKINNING_ROLLOUT/`) kept fill, background, border and text colors out of the reset, and this section said so by naming only textures, borders and fonts. The owner reversed that. Every HUD text and label color, bar fill, background, border, icon border, glow color and text shadow carries a companion, `<color key>FromSkin` or `fontShadowFromSkin`, a `bool` row defaulting `true` in the AceDB defaults and on the row. While it is on, the surface draws `S.HudTextColor()`, `S.HudLabelColor()`, `S.BarFillColor()`, `S.Color(name)` for a background or border, or `S.GlowColor()`, and a string draws its face, size, flags and shadow through **`S.HudFont(fs, opts)`**, because a 12.0.7 client draws no shadow set on a FontString at runtime. While it is off, the stored value draws, and the swatch stays live under options-ui-§17's rule. Every skin states its own `bar.bg`, `bar.border`, `icon.border`, `glow.color` and `cover.dim`, and Ka0s Default's do not move. `S.BarGloss(statusBar, fromSkin)` replaces a host's gloss layer. A stored value is the fallback for a degraded facade, so a follow read never draws an owner token's default over the player's color with the library absent.
- **Class and meaning colors come first.** A class-colored bar, an interrupt or uninterruptible state, a pandemic or running-out tint and any `sem.*` meaning keep their branch, ahead of the companion, and get no companion (§4, §9). `useClassColor` set means class color whatever the companion says.
- **A skin's None bar border defers; a real style wins.** `None` in a skin's `bar.borderStyle` is no border of the skin's own, so it hands back the player's stored *Show border*, style and thickness, companion on or off, and those rows stay live. A real style wins with the companion on: Azeroth, High Contrast, WoW Default and WoW Midnight state one, so a bar with *Show border* off draws that edge. A host reads all three through **`S.BarBorder(style, show, size, fromSkin)`** and never gates on the stored toggle ahead of the call. A default that means "no border" has to say so, as `None` or `borderShow` false: under None the library cannot tell a shipped default from a pick.
- **Moved once more, on the re-vendor of `LibKa0s v1.85.0`.** A new default reaches new profiles only, so existing profiles are migrated too (owner ruling of 2026-11-01), which overwrites choices players made. One per-profile step in the addon's migration runner (savedvariables) calls **`Skin.FollowOnce(profile, keys)`** from `Database:Init` and every `OnProfileChanged`, always with the profile root, its keys naming each companion as a dotted path built per entry. `FollowOnce` reads and writes the per-profile record `profile.skin.fullSkinReset`, which keeps it from running twice, so a companion the player turns off afterward stays off. The record defaults `false` and survives every Defaults path. The step names the companion, never the color or the pick, so a stored value stays exactly as it was for a player who turns the companion off; a flags key is listed only where its reader is on `S.FontFlags`. It never lists font size, a class or meaning color, `skin.ignorePanel` or `skin.ignoreFonts`. It is tested on stored partial values, and on the library absent, where it writes the record itself. The steps are the library's Options document, *Moving to this version*.
- ***Ignore fonts* covers the HUD (from `LibKa0s v1.81.0`, owner ruling of 2026-10-30).** While the owner ignores fonts (§3), HUD text does not follow the skin for face or outline. For `hud.font` and `hud.outline`, `S.Resolve` answers the HUD element's own stored value (nil for a stored *from skin*, which names no face of its own), while `S.Token` answers nil and so do `S.BarStyle()`'s `font`, `fontKey` and `outline`; `hud.fontSize` and every other token are unchanged, and the composer's font picker shows the stored face. An addon that resolves a HUD face itself goes through that seam, never around it, and on nil falls back to the element's own stored pick, else its default, before anything reaches `SetFont`, `LSM:Fetch` or a font-object builder.
- **HUD text follows the *Font outline* (from `LibKa0s v1.82.0`, owner ruling of 2026-10-30).** Under *All text* and *HUD text only* `hud.outline` resolves as the skin states it, and under *Off* it answers `""` (§3). Every HUD font setting stores its flags, and the *Font flags* row gains a **From skin** value, the default for every element, which resolves through `skin.outline` to the flag §3 resolves for `hud.outline`: under *All text* and *HUD text only* the skin's flag (`OUTLINE` in every shipped skin, never a literal the addon types), under *Off* none; while *Ignore fonts* is on it resolves to none (§3). A flag the player picked wins over the setting. **Migrated once, on the re-vendor.** On its re-vendor of `LibKa0s v1.82.0` an addon that already stored flags moves every stored flag equal to its own previous default to *From skin*, **once**, as one per-profile step in its migration runner (savedvariables), as *Reset once, on adoption* above does for the HUD style values; only a flag the player changed from that default counts as picked and is kept. An element that stored no flags starts at *From skin*. The resolver is the library's; an addon resolving the stored *From skin* flag itself goes through it, never around it (options-ui-§16, *Every font setting is the whole block*).
- **HUD sizes follow the skin's factor (from `LibKa0s v1.82.0`).** An element that draws the skin's face sizes its text through `S.HudFontSize(size)` (§4, *Text width is skin-invariant*); one drawing a face the player picked keeps the stored size as it is. A host's degraded facade answers `HudFontSize` with the stored size unchanged, so the surface-parity case stays green on a load without the library.
- An addon with no HUD has nothing here.

### 7. What a skin never touches, and the rules it rescopes (MUST)

**Never a Blizzard shared frame.** A skin paints the addon's own frames and the library's. It never restyles `SettingsPanel`'s chrome, a `StaticPopup`, `GameTooltip` itself or `ColorPickerFrame`. Lines the addon writes onto `GameTooltip` take their colors from the skin; the frame keeps Blizzard's look. The `Ka0sMedia_*` picker's pull-out, the collection's only media pull-out (options-ui-§23), is none of these: it is the library's own frame, so it wears the opener's skin and obeys the Scope as a widget on a settings page does (§1). Its font rows keep their own faces (§3).

**No taint.** No `Hide`, `SetParent` or `SetScript` on a Blizzard frame (a skin replaces no Blizzard frame, so events-frames-taint-§3's hidden-parent case never arises); no `SetBackdrop` on a Blizzard template; nothing written into a Blizzard frame's table. The state a primitive records (prior colors, alpha, font, the holders it created) lives in a weak-keyed table on the library, never on the frame.

**No leak through AceGUI's pool.** A painted AceGUI widget follows options-ui-§19 exactly: everything the paint changed is restored, and its holders hidden, by that widget's `"OnRelease"` before the widget returns to the shared pool, so the next addon to acquire it, Ka0s or not, gets a stock widget. The library paints the widgets its own makers acquire. A host that acquires a widget itself, on an owned page, paints it with `Skin:PaintAce(owner, widget)` (or `Skin:PaintAceTree(owner, container)`) and, because AceGUI keeps one callback per name, attaches any `"OnRelease"` of its own through `Skin:OnRelease(widget, fn)`, which chains it with the restore rather than replacing it. Where another skinning addon has already skinned a widget, the library steps aside and paints nothing.

**The rules rescoped to the Ka0s Default skin.** The look values these rules state are **Ka0s Default's**. An addon that has not adopted skins keeps them exactly as written. An addon that has adopted takes each from its owner's skin through the facade and **MUST NOT** diverge from that skin:

- standalone-windows, *The Ka0s window edge*: the background, the two-line edge, the title and the divider.
- standalone-windows, the close-control bullet: the close mark's rest and hover tints.
- standalone-windows, the `TestStrip` bullet: amber and cyan stay the library's meaning colors under every skin; a skin changes only their legibility, through its `strip.*` tokens.
- options-ui-§5 and options-ui-§8: the header title's face and gold, the divider tracking the title's color, the heading face and the font summary.
- debug-logging-§3: the console's timestamp, tag and content colors, which stay three distinct colors under every skin.

### 8. Commencement

**Adoption is the commencement.** This section, and anti-patterns #107, #110 and #111, bind an addon from the commit in which its own code first calls `Skin:RegisterOwner(<its folder>)`, and from no earlier point: an addon that has not adopted is not a finding under any of it, whatever its release. The collection adopts addon by addon, on the rollout recorded in open-evolutions; a new addon **MAY** adopt from its first release and is not required to before that rollout reaches it. A repository that registers no owner, a library or a documentation-and-tooling repo, has nothing here to audit. One obligation reaches every addon whether or not it has adopted, from its first re-vendor of `LibKa0s v1.78.0`: its Options stub answers `AppearanceTab` and `AppearanceRows` (§3), and `SkinVerb` too from its first re-vendor of `LibKa0s v1.82.0`. A rule this section marks as from a library tag binds an adopted addon from its re-vendor of that tag; a vendor older than the tag is a re-vendor item, not a finding. The audit step is `AUDIT.md`'s *Check skinning*.

### 9. Every surface follows the skin (MUST, owner ruling of 2026-11-01, from `LibKa0s v1.85.0`)

**Change the skin and the whole addon changes with it.** §1 says every visual element paints through the facade; an inventory of the collection found 445 rows, reduced to 31 causes, where something still did not, because a value was typed, a default kept a client pick, or a stored value outranked the skin. This section closes the class. It is decided by cause, not row by row: a surface that does not follow the skin has a cause on the list below, or it is a defect.

- **A surface a skin can reach reads a token.** Every color, texture, border, background, face, shadow and gloss an adopted addon draws comes from a facade primitive or a token read (`S.Color`, `S.Token`, the HUD getters of §6). Where no token describes it, the addon declares an owner token (§1) or the library gains a token (§4).
- **A typed value stays only with a named allow cause.** A color or texture literal in shipped code is taken by one of the kit's shared categories, or it carries a row `{ file, substring, why, cause }` in `Kit.skinValues.rows`. All four fields are required: `why` says why the skin never reaches the value, and `cause` is an id for the exception that holds it, or for the plan item that ruled on it. A row a category already takes, or one that no longer matches a line, is stale and fails. "It looks better this way" is no cause.
- **The exceptions, and only these.** A class is added by an owner ruling and a change to this list, never by an addon.
  - **Meaning colors** (§4): class, item quality, gain and loss, dispel types, cast states, the warning tints (pandemic, running out), and the stat, category, region and data hues where the color is the information. Each keeps its hue under every skin. A meaning with a semantic token reads it (§4); a hue no token describes stays in a named meaning table, never at a call site. It takes no companion, and its branch runs ahead of the skin's (§6).
  - **Game art**: spell and item icons, the addon's own logo, and the feedback players read as the game itself: cooldown sweep, cast spark, shield, button press and flash, proc glow, text selection. What §7 forbids painting (Blizzard's shared frames) and what the client draws and offers no hook for (the minimap right-click menu, the chat frame's font, Group Finder rows) are in this class too. Lines the addon writes into a client frame still take their colors from the skin (§7).
  - **The Leave classes**, each an owner ruling: icon shapes and the minimap ring, since an icon set is not skin data and only the icon's tint follows; text size, which comes from each layout and which the skin only scales (§4); the monospace face (debug-logging-§2); chat lines, whose colors slash-commands and debug-logging fix; window text with no outline, the *HUD text only* default (§3); Ka0s Default keeping the client's resize grip and hover art, which every other skin tints; fades, dims, flat thin bars and the skin values nothing reads yet (corner radius, scroll width); the panels a player authors in PanelMaster, which are the player's content; and DpsRace's clocks, bar colors and missing tracks.
- **HUD colors follow the skin.** Text, labels, bar fill, background, border, glow and shadow are on the skin by default, under §6, and the stored value is what a player turns the companion off to get.
- **The settings panel stays stock by default, and every element in it supports skins.** *Ignore settings panel* stays on by default (§3), and no flip, default or migration writes `skin.ignorePanel` or `skin.ignoreFonts`. That default hides a surface from the player, not from this rule: with the Scope cleared, every element of the panel paints from the skin, the ones a host draws itself included. The Blizzard frames around the pages stay §7's.
- **A shared box wears the skin only for its own use.** AceConfigDialog's delete confirmation wears the skin when a Ka0s profile page raises it, and only then: no client-wide table is written, and every other addon's use of the box stays stock. The Ace profile page itself does not change.
- **Existing profiles move once.** A new default reaches new profiles only, so §6's one-time step migrates the stored ones, overwriting the player's stored choices to follow the skin (owner ruling of 2026-11-01). A class or meaning color is never touched.
- **Two gates enforce it (§1).** `test_skin_values` reads the tree for typed values: it needs git, proves itself with a planted value of each shape on every run, and fails a stale row. `test_skin_switch` builds a probe skin that gives every token its own value, flips to it and back, and fails a declared surface that draws the same, draws nothing, or moved only for reasons of its own. It runs each surface with the Scope cleared and companions on; a second pass holds the Scope ignored and companions off, and excludes a surface marked `scope` or carrying a `companion`. Coverage is the declaration: a surface left out of `Kit.skinSwitch.surfaces` is not tested, and an audit reads the list. Neither gate can see how a surface looks, so the in-client smoke stays the owner's.

**Commencement.** Binding for an adopted addon from its re-vendor of `LibKa0s v1.85.0` (test kit revision 50), and for no addon before it. Anti-pattern #110 is this section as a do-not list. An addon with no HUD owes no step and no companion under §6; it records that as an exception with the command that proves it, and still owes both gates.

### 10. The skin picker's preview (MUST, owner ruling of 2026-11-03, from `LibKa0s v1.85.0`)

**A skin is chosen while the player can see it on the addon.** When the skin picker (§3) shows and the addon's main surface is hidden, the addon enters its **preview mode** and keeps it while the picker is up. The picker's eye button toggles that mode. When the picker closes, by any route, the addon goes back to the state it had when the picker opened. The owner asked for exactly this on 2026-11-03, naming PartyFrameEnhanced's and DropWatcher's eye as the look to copy, and the toggle and the restore as what both lacked.

- **The mode, in this order.** An addon's preview mode is the first of these it has:
  1. **test**: its test mode (options-ui-§15, preview-mode), the `/<slash> test` switch;
  2. **unlock**: its unlocked view, for an addon whose unlocked view is its test mode (`lockIsPreview`, options-ui-§15) or whose only display is its lockable frames, the `/<slash> unlock` switch;
  3. **window**: its primary window, the launcher's *Show window* (launcher-§2), for an addon with no test mode and no lock;
  4. **console**: for an addon that draws nothing of its own but lines in the client's chat, the debug console (debug-logging) filled with the sample lines its test verb prints, and hidden again on close when the picker or the eye opened it (owner's answer for PrettyChat, 2026-11-03).

  An addon **MUST NOT** pick a later mode while it has an earlier one: unlocking an addon that has a test mode moves its frames rather than showing them. Each rostered addon's mode is recorded in `ADDONS.md`, in the *Skin picker preview* column, and an audit checks the host's `spec.preview.mode` against it.
- **"The main surface is hidden" means, per mode:** for **test**, test mode is off and the primary window, where there is one, is not shown; for **unlock**, the frames are locked; for **window** and **console**, the window is not shown. A host that answers no `isShown` counts as hidden.
- **Auto-enter, on a fresh show only.** When the picker shows afresh (§3: the first-run picker, `/<slash> skin`, the queue's handover, `O.SkinNotice`), the library records `{ active, shown }` on that owner's picker record, then, if the main surface is hidden and the mode is off, calls `enter("picker")` and raises the picker over what it opened. A picker shown while the surface is already up enters nothing. A repeat show while the picker is up records nothing again.
- **The eye toggles, and shows its state.** The eye calls `exit("eye")` when the mode is on and `enter("eye")` when it is off. It is drawn lit while the mode is on and dimmed while it is off, and its tooltip names the mode and its state (the library's `PREVIEW_<MODE>_ON` / `_OFF` strings, for example *Preview: test mode is on. Click to turn it off.* and *Preview: the frames are locked. Click to unlock them.*), redrawn when the eye is clicked under the pointer. The library draws it; a host draws no eye of its own.
- **Every close route restores the opening state.** Apply, *Apply to all*, the gear, the close control, Escape and `O.HideSkinPicker` all pass through the library's one close, which runs `exit("picker")` when the mode is on now and was off at open, and `enter("picker")` when it was on at open and the eye turned it off. It runs before `spec.onClose` and before the queue shows the next owner, so two addons' modes never overlap. Hiding UIParent (Alt-Z) is not a close. A queued picker dismissed before it showed recorded nothing and restores nothing.
- **Enter and exit go through the addon's own write seam.** Each is the same handler the slash verb, the launcher's menu entry and the Master-controls checkbox use (launcher-§2, options-ui-§15): `NS.SetTestMode`, the lock row's stored path through `SetByPath`, `Schema:Set`, never a frame call or a raw SavedVariables write around it. So the panel, the launcher and the slash command stay in step, and the addon's combat refusals still apply: a refused `enter` (a start during combat, a secure frame in lockdown) changes nothing, the recorded state stays as it was, and the restore undoes only a change that actually happened. A test mode that ended at combat start is already off when the picker closes, so its restore finds nothing to undo. A restore the host refuses while `InCombatLockdown()` answers true is parked on the library's end-of-combat park and asked once more when combat ends, unless that owner's picker is up again by then; the host adds no park of its own.
- **Unlock is a stored setting.** An unlock host's mode is its stored lock, so a `/reload` while the picker is up leaves the frames unlocked until `/<slash> lock`. No persistence is added for the preview; the host's smoke step says so.
- **The contract is the library's.** The host passes `spec.preview` to `O.SkinPicker`, `O.SkinNotice` and `O.SkinVerb` (OptionsSkinPicker minor 11):

  ```lua
  preview = {
    mode     = "test",              -- "test" | "unlock" | "window" | "console": the eye's wording
    enter    = function(why) end,   -- why: "picker" | "eye"; the addon's own write seam
    exit     = function(why) end,
    isActive = function() return NS.IsTestMode() end,
    isShown  = function() return NS.IsWindowShown() end,  -- optional; absent counts as hidden
  }
  ```

  `spec.onPreview`, the one-shot eye of `LibKa0s v1.78.0`, keeps working in the library for an addon that has not moved: no auto-enter, no restore. When both are passed, `spec.preview` wins. In a Ka0s host on `LibKa0s v1.85.0` it is a finding.
- **The no-preview case (documented).** An addon with no surface of its own to preview passes no `spec.preview` and no `onPreview`, so the picker draws no eye and enters nothing. **PremadeGroupsFilterExtension** is the one today: its panel lives inside PremadeGroupsFilter's dialog, which the player opens from the Group Finder, and it has no window, test mode, lock or console sample of its own. The case is recorded in `ADDONS.md` as `none` with that reason, owes no deviation row, and is the only answer that leaves the eye off. A new no-preview addon is added by an owner ruling and a change to that column.

An eye that only enters its mode, a mode left on after the picker closed, or an enter or exit around the write seam is **anti-pattern #111**.

**Commencement.** Binding for an adopted addon from its re-vendor of `LibKa0s v1.85.0` (OptionsSkinPicker minor 11), and for no addon before it. Until then a vendored `onPreview` eye is a re-vendor item, not a finding.
