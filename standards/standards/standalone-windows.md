## Standalone windows / data browsers

options-ui governs the **options** surface. An addon's own **main window** — a data browser, log, tracker, or dashboard — is a different surface with different rules. Reference implementation (in the collection): the standalone loot-history browser (a resizable, movable data-browser window with a tab strip and a scrolling record list).

- **MUST** be a plain **non-secure** `CreateFrame("Frame")` (movable/resizable) — **not** a Blizzard Settings canvas, **not** a secure/protected frame. A non-secure window touches no protected functions, so it needs **no combat-lockdown gate** and may open/refresh in combat. (Secure/action-button content is the exception and follows events-frames-taint-§2.)
- **MUST** register the window in `UISpecialFrames` so `Escape` closes it and it joins the standard close-stack.
- **MUST** persist window position and size in SavedVariables (e.g. `db.global.settings.window`), restored on open. **SHOULD** clamp to a readable minimum size and `SetClampedToScreen(true)`.
- **SHOULD** expose a scale setting (e.g. `windowScale`) applied via `frame:SetScale`.
- **SHOULD** use a tab strip with **lazy per-tab content build** — build each tab's body on first show, not up front.
- **MUST** take the window's look from `LibKa0s-Core-1.0`'s shared `SKIN` table and `ApplySkin(frame)` seam — stock Blizzard textures, no shipped *texture/border* art — rather than building a private lookalike (anti-patterns #47). Ownership runs the other way round from how it used to: the seam is the library's, and the debug console consumes the same one, so a re-skin has one touch point across the whole collection. A host **MAY** override per-window via the descriptor's `skin` field where a module offers it. The sanctioned media a Ka0s addon draws with are the **shared library payload** — the icon catalog, the monospace face and the bar textures at `libs/LibKa0s/media/` (library-stack-§8) — plus the **addon logo** it ships itself (options-ui-§5 / layout-§3). All of it is expected and **MUST NOT** be flagged as styling deviations in an audit. What an audit **SHOULD** flag is the opposite: a *private* copy of a mark the library already carries (anti-patterns #63).

### The Ka0s window edge

The shared seam decides the look; this is what it draws, and it is **normative** so a new addon inherits it without a decision and an audit has something to compare against. It became the definition after five debug consoles were put side by side and did not read as one suite of addons: two hosts had converged on this treatment for their own windows and overridden the library to keep matching it, while three sat on the library's old 12px `UI-Tooltip-Border`. Specified in `LibKa0s-Core-1.0` from **Core minor 3** (LibKa0s v1.3.0).

| Part | Value | Drawn by |
|---|---|---|
| Background | `Interface\Buttons\WHITE8x8` at `0.06, 0.06, 0.08, 0.92` | `SetBackdrop` + `SetBackdropColor` |
| Outer edge | the same flat white texture at `edgeSize = 1`, inset 1 on all four sides, tinted **black** (`0, 0, 0, 1`) | `SetBackdropBorderColor` |
| Inner highlight | a 1px child frame inset one pixel on both axes, tinted `0.24, 0.24, 0.27, 0.85` | a `BackdropTemplate` child `ApplySkin` creates **once** |
| Title | Blizzard gold, `1.0, 0.82, 0.0` | `frame.title:SetTextColor` |
| Divider | `0.24, 0.24, 0.27, 0.85` | `frame.divider:SetColorTexture` |

- The edge is **two lines, not one**: a hard black outer border with a lighter gray line just inside it. A single-line border of either color is the deviation, and it is the one that is hardest to see in a screenshot taken on its own — it only reads as wrong beside a window that has both.
- A window **MUST NOT** draw an edge that **diverges** from this one. Where `LibKa0s-Core-1.0` is reachable, `ApplySkin` **SHOULD** be what draws it — assign `frame.title` and `frame.divider` first and it tints them; omit either and it skips that call. A host helper that skins the addon's own windows is **not** a deviation and is often necessary (a main window is the host's frame, and the host may want one re-skin seam of its own); it **MUST** produce exactly the values above, and **SHOULD** delegate to `Core.ApplySkin` rather than restate them. The **same** treatment therefore covers the main window, the debug console, the console's copy window and the perf panel, which is the point — a user with four Ka0s addons open should not be able to tell which of them drew which window.
- A host **MAY** pass a module's `applySkin` **function** hook where one exists (debug-logging) — to route the module's window through the host's own re-skin seam, or for chrome differing in **shape** (an extra element, a different anchor). What an audit **SHOULD** flag is a hook or a helper whose **output differs** from the table above, not its existence: a second implementation that agrees is redundancy, and one that disagrees is the drift this section exists to end (anti-patterns #47).
- **The close control draws the shared mark, and it has to be told who is asking.** `MakeCloseButton(parent, onClick, addonName)` draws the catalog's `close` icon in an 18×18 slot with the art inset, gray at rest and red under the pointer; called with two arguments it draws the multiplication sign it always drew. The third argument is the addon's own **folder** name and cannot be inferred — the library is vendored, so there is no one path to it (library-stack-§8, Core minor 6 / LibKa0s v1.10.0).
- **One wrapper, and every close control goes through it (MUST).** An addon **MUST** wrap the seam exactly once, in its `LibKa0s-Core-1.0` setup file — a one-line passthrough that supplies `addonName` from the file's own first vararg — and every close control it builds, on any window, **MUST** be built through that wrapper. A **direct two-argument call to the factory is a defect on sight**, wherever it appears: a main window, a modal, an export panel, or a shared module's decoration hook. This was a **SHOULD** until v2.32.0 and the collection paid for it twice in one week — once inside the library (a forwarder that dropped the argument, anti-patterns #64) and once in an addon (a decoration hook that never passed it, #65) — each producing one window wearing the mark beside another wearing `×`. **What this MUST binds is the library's glyph, and the bullet below is its only exception** — a host that has reasoned its way to a close control of its own, on windows of its own, is under that bullet rather than in breach of this one. Nothing there softens the direct-call rule: a two-argument call to `lib.MakeCloseButton` is a defect wherever it appears, in an addon that took the glyph and in one that declined it alike.
- **A reasoned decline is a terminal compliant state, and it costs four conditions (MUST).** The bullet above and the SHAPE bullet below said different things about the same window until this one was written. One made every close control an addon builds a wrapper call; the other let a host draw its own. `BankLedger/core/CoreSetup.lua:117-129` declines the wrapper in writing and closes its own title bars with a 24×24 class-colored control of its own, which made it compliant under the second bullet and a defect on sight under the first — and an auditor cannot grade a repository against a section that says both, so the grade came down to which bullet was read first. The reconciliation is that the decline is **allowed and terminal**, not tolerated pending adoption, when **all four** of these hold, and is a deviation the moment one of them stops:
  1. **The host's own windows only.** A window a **library** draws — the debug console, its copy window, the perf panel — is never the exception; those keep `MakeCloseButton` unconditionally, for the reason the SHAPE bullet below gives.
  2. **The same shared `close` mark, resolved through the addon's own media seam** (`NS.Icon`, library-stack-§8), so the two implementations agree on the art and differ only in size and hover tint. A private glyph, or a bare `×` where the catalog is reachable, is not a decline — it is anti-patterns #63, and it is indistinguishable on screen from the dropped-argument regression #65 exists to catch.
  3. **Exactly one host factory, and every close control the host builds goes through it.** Greppability is what the wrapper MUST actually buys (see the next bullet), and the exception keeps it rather than trading it away: `BankLedger/modules/Browser.lua:98` is the measured shape — one `B:MakeCloseButton`, reached by the ledger (`modules/Browser.lua:1047`), the session window (`modules/SessionWindow.lua:485`) and the export modal (`modules/Export.lua:362`), and by nothing else. Its fourth close control, on the export copy window, is not the host's to draw at all: that window is `LibKa0s-Widgets-1.0`'s `CopyWindow`, so it wears the library's mark under condition 1, and the decline never reaches it.
  4. **A row in the addon's `docs/ARCHITECTURE.md` deviation register** naming this section, the date it was decided and the condition that ends it (`audit-review-history`). A decline argued only in a code comment or a closed issue is **not** ratified, and an audit is right to file it — as the **missing register row**, not as a MUST breach against each title bar. That distinction is the whole practical difference this bullet makes: the cure is one row in one file, not four rewritten title bars a player would see change for no reason.

  **One decline in the collection, and the count is worth stating because it has been carried wrong.** BankLedger holds the only live decline in the collection. LootHistory's — recorded at `LootHistory/core/CoreSetup.lua:19-26` — **expired with LibKa0s v1.10**, when the library's close began drawing this collection's own mark once it was told which folder was asking; LootHistory adopted the wrapper at `LootHistory/core/CoreSetup.lua:167`, and the multiplication sign is now what a degraded install gets rather than a design choice. Any document still naming the two together is a release stale.
- **Why it has to be a MUST rather than a convention.** Nothing can report the omission. The factory receives no name, builds no texture path, and draws a perfectly good button; a texture path that is never built draws nothing and **raises nothing**. So lint is silent, every suite stays green, and the sole witness is a person looking at two windows side by side — which is why both measured instances were found by a screenshot and neither by a gate. The wrapper does not make the mistake impossible; it makes it **greppable**, which is the most an out-of-game toolchain can offer: `grep -rn 'MakeCloseButton(' --include='*.lua' | grep -v '/libs/'` **MUST** return only the wrapper's own definition and calls to the wrapper. Under a ratified decline the same grep is still the gate and still returns one factory and its callers — the host's own definition, the windows that reach it, and a call to `lib.MakeCloseButton` only where the addon decorates a window the **library** owns (debug-logging-§12). What it must never return is two factories, or a call site reaching neither.
- **A title-bar control strip draws from the catalog (MUST).** Where a window offers controls beside its title — lock, settings, reset, minimize, export, a sort direction — the marks **MUST** be the catalog's, at one size and one pitch. This is the surface where a mark beats a word: the strip is a row of small square targets, the vocabulary is short, and it is the same vocabulary in every Ka0s window. Where the mark is drawn from art the addon **SHOULD** keep a fallback ladder beneath it (shipped art → a Blizzard atlas → a plain character), because a texture that fails to load draws nothing and raises nothing.
- **A wide action button keeps its label and gains a mark beside it (SHOULD).** *Export to CSV* with a `spreadsheet`, *Print to Chat* with a `chat` — the mark says where the action lands, the word says what it does, and the label stays centered so a missing icon leaves the button as it was. **SHOULD NOT** replace such a label with a mark alone: on a button that does something outward, "which one posts to guild?" becomes a question answered by hovering.
- **The edge is shared; the close control's SHAPE is the host's.** A window's × comes from `LibKa0s-Core-1.0`'s `MakeCloseButton`, and a host **MAY** draw a different one on **its own** windows, but only under the **four conditions** the decline bullet above sets out: where the design genuinely calls for it (a large data browser reasonably closes with a larger, more visible glyph than a small diagnostic window), where the mark is still the catalog's, where one host factory draws every one of them, and where the register carries the row. It is that bullet, not this parenthesis, that decides when the design has called for it. Read as a free hand, which is how it read until that bullet was written, this MAY contradicted the wrapper MUST outright. But a window a **library** draws — the debug console, its copy window, the perf panel — **MUST** keep the library's, and a host **MUST NOT** push its own glyph onto them through a module's `makeCloseButton` hook. Those windows belong to the library and are the surface a user compares across addons; the host's main window is not. Reserve the hook for a close control genuinely **different in kind**, and note that no addon in the collection needs it.
- Changing any value here is a **standard** change, not a library one: it alters every Ka0s window at once, so it lands in this section first and in `Core.SKIN` second.
- **MUST** pool rows for any high-churn list inside the window (events-frames-taint-§6) — never one frame per record.
- **SHOULD** provide explicit window verbs (`show` / `hide` / `toggle`); bare `/<slash>` opens the settings panel and `/<slash> help` prints the index (slash-commands-§4). The **launcher is no longer an "and/or"** — every addon ships one, and an addon with a primary window gets a **_Show window_ entry in the launcher's right-click menu**, on its minimap button and its broker row alike, which toggles that window through the same handler as the `toggle` verb and is grayed while the addon is disabled (launcher-§2). Left-click opens the settings panel on every addon; until v2.67.0 it toggled the primary window.
