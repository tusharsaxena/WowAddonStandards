## Standalone windows / data browsers

options-ui governs the **options** surface. An addon's own **main window** — a data browser, log, tracker, or dashboard — is a different surface with different rules. Reference implementation (in the collection): the standalone loot-history browser (a resizable, movable data-browser window with a tab strip and a scrolling record list).

- **MUST** be a plain **non-secure** `CreateFrame("Frame")` (movable/resizable) — **not** a Blizzard Settings canvas, **not** a secure/protected frame. A non-secure window touches no protected functions, so it needs **no combat-lockdown gate** and may open/refresh in combat. (Secure/action-button content is the exception and follows events-frames-taint-§2.)
- **MUST** register the window in `UISpecialFrames` so `Escape` closes it and it joins the standard close-stack.
- **MUST** call `SetToplevel(true)` and sit in the window tier of frame-layering-§1: `MEDIUM` for a window kept up while playing, `HIGH` for a browser opened to read and closed. A popup it opens closes with it (frame-layering-§4).
- **MUST** persist window position and size in SavedVariables (e.g. `db.global.settings.window`), restored on open. **SHOULD** clamp to a readable minimum size and `SetClampedToScreen(true)`.
- **SHOULD** expose a scale setting (e.g. `windowScale`) applied via `frame:SetScale`.
- **SHOULD** use a tab strip with **lazy per-tab content build** — build each tab's body on first show, not up front.
- **MUST** take the window's look from `LibKa0s-Core-1.0`'s shared `SKIN` table and `ApplySkin(frame)` seam — stock Blizzard textures, no shipped *texture/border* art — rather than building a private lookalike (anti-patterns #47). An addon that has adopted skins takes it through the LibKa0s Skin facade with itself as the owner (skinning-§1), and the skin's Ka0s Default draws exactly what this seam draws. Ownership runs the other way round from how it used to: the seam is the library's, and the debug console consumes the same one, so a re-skin has one touch point across the whole collection. A host **MAY** override per-window via the descriptor's `skin` field where a module offers it. The sanctioned media a Ka0s addon draws with are the **shared library payload** — the icon catalog, the monospace face and the bar textures at `libs/LibKa0s/media/` (library-stack-§8) — plus the **addon logo** it ships itself (options-ui-§5 / layout-§3). All of it is expected and **MUST NOT** be flagged as styling deviations in an audit. What an audit **SHOULD** flag is the opposite: a *private* copy of a mark the library already carries (anti-patterns #63).

### The Ka0s window edge

The shared seam decides the look; this is what it draws, and it is **normative** so a new addon inherits it without a decision and an audit has something to compare against. **These are the Ka0s Default skin's values (v2.89.0).** An addon that has adopted skins draws the edge, title, divider and close tints from its owner's skin through the LibKa0s Skin facade and **MUST NOT** diverge from that skin; an addon that has not adopted keeps these exact values (skinning-§7). It became the definition after five debug consoles were put side by side and did not read as one suite of addons: two hosts had converged on this treatment for their own windows and overridden the library to keep matching it, while three sat on the library's old 12px `UI-Tooltip-Border`. Specified in `LibKa0s-Core-1.0` from **Core minor 3** (LibKa0s v1.3.0).

| Part | Value | Drawn by |
|---|---|---|
| Background | `Interface\Buttons\WHITE8x8` at `0.06, 0.06, 0.08, 0.92` | `SetBackdrop` + `SetBackdropColor` |
| Outer edge | the same flat white texture at `edgeSize = 1`, inset 1 on all four sides, tinted **black** (`0, 0, 0, 1`) | `SetBackdropBorderColor` |
| Inner highlight | a 1px child frame inset one pixel on both axes, tinted `0.24, 0.24, 0.27, 0.85` | a `BackdropTemplate` child `ApplySkin` creates **once** |
| Title | Blizzard gold, `1.0, 0.82, 0.0` | `frame.title:SetTextColor` |
| Divider | `0.24, 0.24, 0.27, 0.85` | `frame.divider:SetColorTexture` |

- The edge is **two lines, not one**: a hard black outer border with a lighter gray line just inside it. A single-line border of either color is the deviation, and it is the one that is hardest to see in a screenshot taken on its own — it only reads as wrong beside a window that has both.
- A window **MUST NOT** draw an edge that **diverges** from this one (in an addon that has adopted skins, from its owner's skin). Where `LibKa0s-Core-1.0` is reachable, `ApplySkin` **SHOULD** be what draws it — assign `frame.title` and `frame.divider` first and it tints them; omit either and it skips that call. A host helper that skins the addon's own windows is **not** a deviation and is often necessary (a main window is the host's frame, and the host may want one re-skin seam of its own); it **MUST** produce exactly the values above, and **SHOULD** delegate to `Core.ApplySkin` rather than restate them. The **same** treatment therefore covers the main window, the debug console, the console's copy window and the perf panel, which is the point — a user with four Ka0s addons open should not be able to tell which of them drew which window.
- A host **MAY** pass a module's `applySkin` **function** hook where one exists (debug-logging) — to route the module's window through the host's own re-skin seam, or for chrome differing in **shape** (an extra element, a different anchor). What an audit **SHOULD** flag is a hook or a helper whose **output differs** from the table above, not its existence: a second implementation that agrees is redundancy, and one that disagrees is the drift this section exists to end (anti-patterns #47).
- **The close control draws the shared mark, and it has to be told who is asking.** `MakeCloseButton(parent, onClick, addonName)` draws the catalog's `close` icon in an 18×18 slot with the art inset, gray at rest and red under the pointer (Ka0s Default's tints; under another skin, the owner's skin's rest and hover tints, skinning-§7; from `LibKa0s v1.105.0` every skin's `close.rest` follows its `icon.tint`, so the close rests in the same color as the marks beside it, *Title-bar controls*, below); called with two arguments it draws the multiplication sign it always drew. The third argument is the addon's own **folder** name and cannot be inferred — the library is vendored, so there is no one path to it (library-stack-§8, Core minor 6 / LibKa0s v1.10.0).
- **One wrapper, and every close control goes through it (MUST).** An addon **MUST** wrap the seam exactly once, in its `LibKa0s-Core-1.0` setup file — a one-line passthrough that supplies `addonName` from the file's own first vararg — and every close control it builds, on any window, **MUST** be built through that wrapper, **or through `LibKa0s-Widgets-1.0`'s `W.HeaderButtons`** (WidgetsHeader minor 1, `LibKa0s v1.105.0`; *Title-bar controls*, below), which calls `MakeCloseButton(parent, onClick, owner)` with the three arguments itself, or the host's one factory passed as its `makeClose` under a ratified decline. A **direct two-argument call to the factory is a defect on sight**, wherever it appears: a main window, a modal, an export panel, or a shared module's decoration hook. This was a **SHOULD** until v2.32.0 and the collection paid for it twice in one week — once inside the library (a forwarder that dropped the argument, anti-patterns #64) and once in an addon (a decoration hook that never passed it, #65) — each producing one window wearing the mark beside another wearing `×`. **What this MUST binds is the library's glyph, and the bullet below is its only exception** — a host that has reasoned its way to a close control of its own, on windows of its own, is under that bullet rather than in breach of this one. Nothing there softens the direct-call rule: a two-argument call to `lib.MakeCloseButton` is a defect wherever it appears, in an addon that took the glyph and in one that declined it alike.
- **A reasoned decline is a terminal compliant state, and it costs four conditions (MUST).** The bullet above and the SHAPE bullet below said different things about the same window until this one was written. One made every close control an addon builds a wrapper call; the other let a host draw its own. BankLedger declines the wrapper in writing (`core/CoreSetup.lua`, the comment headed `` `lib.MakeCloseButton` IS DELIBERATELY NOT REPUBLISHED ``) and closes its own title bars with a 24×24 class-colored control of its own, which made it compliant under the second bullet and a defect on sight under the first — and an auditor cannot grade a repository against a section that says both, so the grade came down to which bullet was read first. The reconciliation is that the decline is **allowed and terminal**, not tolerated pending adoption, when **all four** of these hold, and is a deviation the moment one of them stops:
  1. **The host's own windows only.** A window a **library** draws — the debug console, its copy window, the perf panel — is never the exception; those keep `MakeCloseButton` unconditionally, for the reason the SHAPE bullet below gives.
  2. **The same shared `close` mark, resolved through the addon's own media seam** (`NS.Icon`, library-stack-§8), so the two implementations agree on the art and differ only in size and hover tint. A private glyph, or a bare `×` where the catalog is reachable, is not a decline — it is anti-patterns #63, and it is indistinguishable on screen from the dropped-argument regression #65 exists to catch.
  3. **Exactly one host factory, and every close control the host builds goes through it.** Greppability is what the wrapper MUST actually buys (see the next bullet), and the exception keeps it rather than trading it away: BankLedger is the measured shape — one `B:MakeCloseButton` (`modules/Browser.lua`), reached by the ledger (`EnsureFrame` in `modules/Browser.lua`), the session window (`ensureFrame` in `modules/SessionWindow.lua`) and the export modal (`EnsureFrame` in `modules/Export.lua`), and by nothing else. Its fourth close control, on the export copy window, is not the host's to draw at all: that window is `LibKa0s-Widgets-1.0`'s `CopyWindow`, so it wears the library's mark under condition 1, and the decline never reaches it.
  4. **A row in the addon's `docs/ARCHITECTURE.md` deviation register** naming this section, the date it was decided and the condition that ends it (`audit-review-history`). A decline argued only in a code comment or a closed issue is **not** ratified, and an audit is right to file it — as the **missing register row**, not as a MUST breach against each title bar. That distinction is the whole practical difference this bullet makes: the cure is one row in one file, not four rewritten title bars a player would see change for no reason.

  **One decline in the collection, and the count is worth stating because it has been carried wrong.** BankLedger holds the only live decline in the collection. LootHistory's — recorded in LootHistory `core/CoreSetup.lua`, the comment headed `` `Core.MakeCloseButton` USED TO BE DECLINED HERE `` — **expired with LibKa0s v1.10**, when the library's close began drawing this collection's own mark once it was told which folder was asking; LootHistory adopted the wrapper (`NS.MakeCloseButton` in `core/CoreSetup.lua`, which returns `lib.MakeCloseButton(parent, onClick, addonName)`), and the multiplication sign is now what a degraded install gets rather than a design choice. Any document still naming the two together is a release stale.
- **Why it has to be a MUST rather than a convention.** Nothing can report the omission. The factory receives no name, builds no texture path, and draws a perfectly good button; a texture path that is never built draws nothing and **raises nothing**. So lint is silent, every suite stays green, and the sole witness is a person looking at two windows side by side — which is why both measured instances were found by a screenshot and neither by a gate. The wrapper does not make the mistake impossible; it makes it **greppable**, which is the most an out-of-game toolchain can offer: `grep -rn 'MakeCloseButton(' --include='*.lua' | grep -v '/libs/'` **MUST** return only the wrapper's own definition and calls to the wrapper. Under a ratified decline the same grep is still the gate and still returns one factory and its callers — the host's own definition, the windows that reach it, and a call to `lib.MakeCloseButton` only where the addon decorates a window the **library** owns (debug-logging-§12). What it must never return is two factories, or a call site reaching neither.
- **A title-bar control strip draws from the catalog (MUST).** Where a window offers controls beside its title — lock, settings, reset, minimize, export, a sort direction — the marks **MUST** be the catalog's, at one size and one pitch. This is the surface where a mark beats a word: the strip is a row of small square targets, the vocabulary is short, and it is the same vocabulary in every Ka0s window. Where the mark is drawn from art the addon **SHOULD** keep a fallback ladder beneath it (shipped art → a Blizzard atlas → a plain character), because a texture that fails to load draws nothing and raises nothing.
- **Title-bar controls: extras · settings · close, with a settings mark on every window (MUST at adoption, v2.113.0, owner ruling Q3 of 2026-11-16).** Every window's title-bar marks are right-aligned and read, left to right, **the window's own extras · settings · close**: the close in the corner, the settings mark beside it, the extras inward of it in the window's own order (LibKa0s#86). They share one size, one pitch and one paint path: an 18 px slot with 12 px art from the LibKa0s icon set, 6 px from the corner and 6 px apart, colored as *Colors* below says. `LibKa0s-Widgets-1.0`'s **`W.HeaderButtons(bar, spec)`** (WidgetsHeader minor 1, `LibKa0s v1.105.0`) builds the strip, and an addon that has adopted it builds every window's marks with it rather than placing them by hand.
  - **Settings is on every window.** The mark opens the owning addon's settings: by default the opener `LibKa0s-Launcher-1.0` registers for the addon's folder (`LibKa0s-Core-1.0` minor 18's `OpenSettings(owner)`), which is why each window's `addonName` (its `owner`) **MUST** equal the folder the launcher registered under (the launcher descriptor's `name`, or its `owner` where it differs); otherwise the mark opens nothing and says nothing. A window whose settings are its own page passes its own opener. A window that would cover the settings panel hides itself first (`hideOnSettings`).
  - **Opting out costs a reason.** A window drops the settings mark only with `settings = false` **and** a `settingsOptOut` reason, which the library refuses to build without; the reason names why the mark has nowhere better to go, such as a picker opened from a settings row with the panel already beneath it. The library's own opt-out is its icon browser. A HUD display's drag strip is the one place the mark is **opt-in** (`spec.settings = true`), because a strip shows only while the display is unlocked.
  - **Every title-bar control carries a tooltip (MUST, owner ruling of smoke round 1, 2026-11-16).** Every mark, the close and the debug console's included, shows a one-line tooltip on hover and hides it on leave: a chrome tooltip, attached and centered **above** the control, below it only without room above (*Tooltip placement*, below), through `LibKa0s-Tooltip-1.0`'s `PlaceAttached`. The library's hook is `AttachTitleTip(btn, words, owner)`, the line in the owner's `gtip.title`. The close says "Close" (`CLOSE_STRINGS.CLOSE_TIP`; `SetCloseTip(owner, words)` records a translation, and `W.HeaderButtons` takes `closeTip`). `W.HeaderButtons` shows each mark's `tip` and `settingsTip`, and its first cut's `tips = false` is retired (accepted, never read). A HUD drag strip's mark with no host words shows the library's ("Drag to move", "Open settings", "Close"). The debug console's exception (debug-logging-§13) is withdrawn: its tooltips open above the control, so they no longer cover the log's first line, which was the exception's reason.
  - **Colors (MUST, owner ruling of smoke round 1, 2026-11-16; the distinct hover, smoke round 2, 2026-11-17).** Every control on a window's title bar, in every skin, follows one rule. **At rest** it is `icon.tint`, the close and the debug console's **Diagnostics** link included (every skin's `close.rest` follows `icon.tint`). **Under the pointer** it keeps the hover glow it already draws and is tinted **`text.link`**, the Diagnostics link's former rest color (Ka0s Default's orange, `1, 0.5, 0`). The close is the exception: it lights **`close.hot`**, red. Before this ruling a mark lit `icon.hot`, which in several skins read as a faint glow only. **The hover is another color than the rest, not a brighter shade of it, in every skin** (owner ruling of smoke round 2): the library measures the two in CIEDE2000 (ΔE00, sRGB, D65) and holds `text.link` at least **20** off `icon.tint` in every skin, the lowest the owner accepted, and at least **25** in Azeroth, Glass, WoW Midnight and WoW Forever, the four whose hover read as a shade, which `LibKa0s v1.105.0` raised by moving `text.link` alone (`tests/test_skin_defs.lua`). An addon that paints a title-bar control from an owner token over `icon.tint` or `text.link` **MUST** hold the same floor under every skin. A control whose color carries its **state** keeps its state colors: the console's Debug ON/OFF label stays `sem.on` / `sem.off`, with its `text.accent` hover. The library's suite pins this per skin (`tests/test_tool_windows_skin.lua`). A HUD drag strip draws from its own palette (`handle.*`, `icon.tint`, `icon.hot`) and is not a window's title bar here. A host that overrides `icon.tint` with an owner token sets `close.rest` with it, so its close stays in step. A window's **footer buttons** hover to the same floor, a primary one by its fill (*The footer*, below).
  - **The `help` mark is not a default extra**, because the library's art for it reaches only an addon that declares `help` on its `LibKa0s icons:` line; an addon that adds a help extra declares it. Every library window's settings mark draws `settings`, so every addon declares that one.
  - **The library's own windows carry the strip from `LibKa0s v1.105.0`**: the debug console (copy · clear · settings · close), the copy window, the perf panel, the sim panel and the skin picker, whose gear moved from its dropdown row into the header; the icon browser opts out. Each control on them carries its tooltip and the colors above. That arrives with the re-vendor and asks nothing of the addon beyond the registered launcher name above.
  - **When it binds.** This is owed by an addon's own windows when the addon adopts `W.HeaderButtons`, tracked by LibKa0s#86 (library-stack-§7, *What a re-vendor owes and what adoption owes*), and the tooltip and color bullets above bind an addon's own title-bar controls on the same terms. A re-vendor to `LibKa0s v1.105.0` alone does not make an addon's hand-built title bar non-compliant; a window adopted onto the strip and then given a hand-placed mark beside it is, and so is an adopted window's control left without a tooltip or painted outside the colors above.
- **A wide action button keeps its label and gains a mark beside it (SHOULD).** *Export to CSV* with a `spreadsheet`, *Print to Chat* with a `chat` — the mark says where the action lands, the word says what it does, and the label stays centered so a missing icon leaves the button as it was. **SHOULD NOT** replace such a label with a mark alone: on a button that does something outward, "which one posts to guild?" becomes a question answered by hovering.
- **Every window marks test and simulated data with the library's strip, directly under its title bar (MUST, v2.110.0, owner ruling of 2026-11-15).** A window that draws test or simulated data satisfies preview-mode's marker rule with `LibKa0s-Widgets-1.0`'s **`TestStrip`** (Widgets minor 13, `LibKa0s v1.75.0`), placed by the strip's docking to the title bar (LibKa0s-Widgets-1.0 Footer and TestStrip docking, Widgets minor 27, `LibKa0s v1.103.0`). From v2.86.0 to v2.109.0 this was a **SHOULD** for a window with a filter bar, whose strip sat between the filter bar and the body, and any other window could mark the mode with a title badge or inline title text. The owner ruled on 2026-11-15 that the strip sits right below the window header in every addon (preview-mode, *Where the strip sits*). The strip:
  - spans the window's full width inside its edge, **directly under the title bar**, above tabs, a filter bar, a toolbar and the body;
  - carries a mark the host passes (a resolved icon the host declares on its `LibKa0s icons:` line like any other, library-stack-§7) and one localized line saying what test mode shows and what ends it;
  - pushes everything below the title bar down by the strip's published height (`TEST_STRIP.HEIGHT`) while it shows, and covers nothing;
  - comes in two flavors, chosen by `opts.kind`: the library's amber for test mode (the default) and its cyan for a simulation (`kind = "sim"`, Widgets minor 14, `LibKa0s v1.76.0`). The color is the library's; a host never passes one. Amber and cyan stay the library's meaning colors under every skin, and a skin changes only their legibility, through its `strip.*` tokens (skinning-§7).

  The library builds and places the strip: the host owns its text (`strip.text`), any tooltip, a two-line compact variant and when it shows, and names the title bar it docks under; it never anchors the strip itself. Once an addon carries `LibKa0s v1.75.0`, a host-built copy of the strip is anti-pattern #47; once it carries `LibKa0s v1.103.0`, a strip anywhere but under the title bar, or anchored by hand, is anti-pattern #118. A window that marks both modes builds one strip per kind at the same dock and shows the one in force. Its header carries no mode word while a strip shows (preview-mode, *One marker per mode on screen*); a minimized window, which hides the strip, keeps the word or a badge in its title bar. **Adoption is blocked until `LibKa0s v1.103.0` is tagged**: until an addon vendors it, a filter-bar window's strip between the filter bar and the body, and a title badge on a window with no filter bar, are re-vendor items, not findings.
- **The edge is shared; the close control's SHAPE is the host's.** A window's × comes from `LibKa0s-Core-1.0`'s `MakeCloseButton`, and a host **MAY** draw a different one on **its own** windows, but only under the **four conditions** the decline bullet above sets out: where the design genuinely calls for it (a large data browser reasonably closes with a larger, more visible glyph than a small diagnostic window), where the mark is still the catalog's, where one host factory draws every one of them, and where the register carries the row. It is that bullet, not this parenthesis, that decides when the design has called for it. Read as a free hand, which is how it read until that bullet was written, this MAY contradicted the wrapper MUST outright. But a window a **library** draws — the debug console, its copy window, the perf panel — **MUST** keep the library's, and a host **MUST NOT** push its own glyph onto them through a module's `makeCloseButton` hook. Those windows belong to the library and are the surface a user compares across addons; the host's main window is not. Reserve the hook for a close control genuinely **different in kind**, and note that no addon in the collection needs it.
- **A window's footer is the library's `Footer` (MUST, v2.110.0).** See *The footer*, below.
- **Tooltips are placed by the window, never by the pointer (MUST, v2.112.0).** A body element's tooltip opens beside the window group and a chrome element's is attached and centered above its control, flipping below only without room above (v2.113.0). See *Tooltip placement*, below.
- Changing any value here is a **standard** change, not a library one: it alters every Ka0s window at once, so it lands in this section first and in `Core.SKIN` second. The values here are the Ka0s Default skin's; the other skins are library data (skinning-§4).
- **MUST** pool rows for any high-churn list inside the window (events-frames-taint-§6) — never one frame per record.
- **SHOULD** provide explicit window verbs (`show` / `hide` / `toggle`); bare `/<slash>` opens the settings panel and `/<slash> help` prints the index (slash-commands-§4). The **launcher is no longer an "and/or"** — every addon ships one, and an addon with a primary window gets a **_Show window_ entry in the launcher's right-click menu**, on its minimap button and its broker row alike, which toggles that window through the same handler as the `toggle` verb and is grayed while the addon is disabled (launcher-§2). Left-click opens the settings panel on every addon; until v2.67.0 it toggled the primary window.

### Window chrome geometry

A Ka0s window stacks its chrome in one order, top to bottom: the **title bar**, the **test or sim strip** while one shows, then the window's own tabs, filter bar and body, and the **footer** where the window has one. Each band's height is a published number, the same under every skin (skinning-§4, *Geometry is skin-invariant*), and a host reads it from where it is published and copies none of them into its own constants file.

| Band | Height | Published as |
|---|---|---|
| Title bar | **30 px** | the skin token `title.height` (`LibKa0s-Skin-1.0`), Ka0s Default's value and so every skin's |
| Test or sim strip | the strip's own | `TEST_STRIP.HEIGHT` (`LibKa0s-Widgets-1.0`, Widgets minor 13, `LibKa0s v1.75.0`) |
| Footer | **24 px** | `FOOTER.HEIGHT` (`LibKa0s-Widgets-1.0`, Widgets minor 27, `LibKa0s v1.103.0`) |

- **The title-bar height is stated here, not changed.** 30 px is the value `title.height` carried before this table existed, and skinning-§4 already held it invariant across skins; v2.110.0 writes it down beside the footer's, as the owner asked ("define the height of the footer as well (e.g how the header height is defined)", 2026-11-15).
- **The footer height is new, and binding (MUST).** A window footer is 24 px tall, read from `FOOTER.HEIGHT`, under every skin. Like the strip's, it is a library constant a host write cannot move, and a footer of another height is anti-pattern #118.
- **The body sits between them.** Its top inset is the title bar's height, plus `TEST_STRIP.HEIGHT` while a strip shows, plus the host's own gap; its bottom inset is `FOOTER.HEIGHT` while the footer shows, plus the host's own gap. A band the player can hide gives its height back to the body while it is hidden.

### The footer (MUST, v2.110.0, owner ruling of 2026-11-15)

A **footer** is the band along a window's bottom edge that carries a status line (a record count, a refresh rate, a database size, a hint) and sometimes a control or two. Every window that has one, a host's window or a library's, **MUST** build it with `LibKa0s-Widgets-1.0`'s **`Footer`** (LibKa0s-Widgets-1.0 Footer and TestStrip docking, Widgets minor 27, `LibKa0s v1.103.0`). The look is the one the collection's combat-meter HUD window drew (in the collection), with no fill of its own under a hairline rule. The owner asked on 2026-11-15 that "the footer of any window that has one should look like" it, in place of the dark band other windows drew. These are the values; the colors are Ka0s Default's, and an adopted addon's footer reads the same tokens from its owner's skin (skinning-§7):

| Part | Value |
|---|---|
| Fill | **none**: the window's own background shows through, and no band is drawn under the footer |
| Divider | a 1 px hairline along the footer's top edge, inset to the window edge, in the skin's `divider` token |
| Left text | the status line, in the muted text token (`text.muted`), left-aligned on the window's side padding |
| Right text | optional, in the same token, right-aligned |
| Control slot | optional, on the right: catalog marks at one size and one pitch, as the title-bar control strip draws them (above) |
| Resize grip | where the window resizes, in the footer's bottom-right corner, with the right text and the control slot to its left |
| Height | **24 px**, `FOOTER.HEIGHT` (*Window chrome geometry*, above) |

- **Built by the library, worded by the host.** The library draws the footer, its divider, its two text slots, the control slot's layout and the grip's corner. The host owns every string (localized, localization), each control's action and tooltip, and when the footer shows. A host that lets the player hide its footer gives its height back to the body while it is hidden.
- **Nothing the body draws passes under the divider.** While the footer shows, the body ends `FOOTER.HEIGHT` above the window's bottom edge, plus the host's own gap.
- **A footer button hovers as a title-bar control does (MUST, owner answer of smoke round 2, 2026-11-17, from `LibKa0s v1.105.0`; a primary button by its fill, the owner's option C of the same round).** A boxed text button along a window's bottom edge, in a `Footer`'s control slot or in the window's own bottom button row, keeps the hover glow it draws, and under the pointer it looks clearly unlike its rest in every skin. A **plain** button's **label** turns the skin's button hover color, `btn.hover`, which the library holds at least 20 ΔE00 off the rest label, the title bar's floor (*Title-bar controls*, *Colors*, above), and legible on the button's fill (at least the rest label's contrast, or 4.5:1). In most skins that color is `text.link`; Azeroth's push button lights `#FFF800`, its link's saturated twin, and a hover that already cleared the floor kept its value. A **primary** button keeps its label at `btnPrimary.text` and changes its **fill** instead: `S.Button` repaints its box in `btnPrimary.hoverBg` under the pointer and in `btnPrimary.bg` on leave. The library holds each skin's `btnPrimary.hoverBg` at least 20 ΔE00 off `btnPrimary.bg`, both composited over the window (a gradient read as the mean of its stops), with the label legible on it by the same contrast test; the token is a step of the skin's own primary fill, with a gradient pair (`btnPrimary.hoverBgTop` / `btnPrimary.hoverBgBottom`) exactly where `btnPrimary.bg` is one. A disabled primary does not hover, and a primary whose `bg` a host remaps through `opts.tokens` without a `hoverBg` keeps its fill under the pointer. `btnPrimary.hover` stays in the schema for a host, and no library painter reads it. Both floors hold in every skin with no exemption, in `tests/test_footer_button_hover.lua`. The library's own are the skin picker's Apply (its primary) and Apply to all (`S.Button`), the icon browser's Choose and Cancel (AceGUI Buttons, painted by SkinAce) and the sim panel's Start and controls, which light `text.link`. A `Footer`'s own marks are icon marks and keep `icon.tint` / `icon.hot`. **When it binds:** a footer button the library's painters draw (`S.Button`, SkinAce's `Button`) takes it from the skin's tokens at the re-vendor. An addon's own hand-painted footer button, and an owner token for one's hover (a label hover or a primary's `hoverBg`), owes it when the addon adopts skins (skinning; library-stack-§7, *What a re-vendor owes and what adoption owes*); a re-vendor to `LibKa0s v1.105.0` alone does not make it non-compliant.
- **What is not a footer.** A drag strip, a sim step panel's controls and a settings page's buttons are not window footers. A modal's button row is not one either. Each keeps the rule that governs it.
- **A footer that is not this is anti-pattern #118:** a filled band (the dark strip the owner retired), a footer drawn from the host's own texture and font strings, one of another height, text in a color other than the muted token, or a resize grip outside its corner. Once an addon carries `LibKa0s v1.103.0`, a host-built footer beside the library's is anti-pattern #47 as well.
- **Adoption is blocked until `LibKa0s v1.103.0` is tagged**, and is blocked rather than overdue until then: a footer an addon built before it vendors that tag is a re-vendor item, not a finding. From its re-vendor of the tag, every footer the addon draws is the library's. A window the **library** draws is the library's to move, in the same release.

### Resizing

A resizable window is laid out many times a second while the player drags its grip, and work that costs nothing once costs a visible stutter when it runs on every size tick. The measured case is Ka0s DPS Race (2026-10-26): its window rebound and redrew its content from data on every size change, so the frame trailed the pointer, and the collection owner asked for smooth resizing on every window, *including ones that are not laggy today*. A window that is fast now gains content later, and the lag arrives with the content rather than with a change anyone reviews as a resize change.

This binds **every standalone window an addon owns that can be resized**, whether the player drags a grip or the size changes by any other means in a continuous run (a size slider being dragged, a scripted resize). A window a library draws — the debug console, its copy windows, the perf panel — is the library's, not the host's.

- **While the window is being sized, per-frame work MUST be limited to cheap layout:** re-anchoring and re-sizing what the new size needs — column widths, the visible row count, scroll ranges, wrapping widths computed from config. On any `OnSizeChanged` call or size tick the window **MUST NOT**:
  - rebind or re-sort a data list;
  - rebuild or redraw a content panel from data;
  - re-read the data store (SavedVariables, a cache of records, a game API);
  - build pooled rows (events-frames-taint-§6) beyond the visible count; a window that grows acquires only the rows now visible.
- **Size changes MUST be coalesced to at most one layout pass per rendered frame.** `OnSizeChanged` can fire more than once in a frame, for the window and for children anchored to it. The handler marks the layout dirty and one pass runs on the next frame; it never runs one pass per call.
- **The full redraw MUST run once, when sizing ends.** Data rebind, content redraw and anything that is measured run on the grip's `OnMouseUp`, after `StopMovingOrSizing()`; where the end cannot be observed, they run after a short quiet with no further size change. The saved size (architecture-§5's *geometry only a drag or a resize determines*) is written then, by its named writer, and **MUST NOT** be written per frame. A debug trace of the resize is one line at the end, not one per tick (debug-logging-§9).
- **Layout during sizing follows the layout rules the standard already has.** Every number the cheap pass sets is computed from the window's new size, from config and from the layout constants (options-ui-§8), and none is read off a state-dependent measurement such as a child's current size, a font string's width or a selected tab's art (options-ui-§13, anti-pattern #70). A pass that measures its own children mid-drag reads the size the previous pass gave them, and a resize is where that feedback shows.
- **One shared helper per addon (SHOULD).** An addon **SHOULD** implement this once, as a single helper that each resizable window hands its cheap layout and its full redraw, rather than once per window. A per-window copy is where one window forgets the coalescing or writes the size per tick.
- **Verification (MUST).** The headless suite **MUST** carry a case that drives a sequence of size changes through a simulated drag (grip down, several size changes across several frames, grip up) and asserts with a spy that the full redraw ran exactly once, after the release, and that the cheap layout ran at most once per simulated frame. The case **MUST** be able to fail (testing-§12): it dies under a handler that calls the full redraw directly. `docs/smoke-tests.md` **MUST** carry the in-game check: drag each resizable window's grip continuously, confirm the content follows the pointer without lag, release, and confirm the content redraws and the size survives `/reload`.

### Tooltip placement (MUST, v2.112.0, owner ruling of 2026-11-15; the chrome rule's side amended in v2.113.0)

A tooltip is placed by **where the hovered element sits in its window**, never by where the pointer is. Two placements cover every case. A tooltip about the window's **content** opens **beside the window**, outside its outer edge, so it covers none of the rows the player is reading or comparing. A tooltip about the window's **chrome** (its title bar, tabs, filter bar or footer) is **attached to the control**, centered on it, directly **above** it, and below it only when the screen has no room above. v2.112.0 put a top-chrome tooltip below its control and a footer's above; the owner's first smoke pass on `LibKa0s v1.105.0` (2026-11-16) found a tooltip under a title-bar mark illegible, because it opened where the pointer was, and ruled every attached tooltip above. The pointer hangs down from its hotspot, so above is the side it never covers. The owner ruled both placements on 2026-11-15, with the measured good case a roll-tracking window's companion panel whose row tooltip opens right of the panel with its top level with the row. Two shapes are ruled out: a tooltip that follows the cursor, and one offset from a corner of the control it describes, which reads as belonging to whatever sits beside it.

**Why it is a rule and not taste.** A tooltip drawn over a list covers the neighbors of the row it describes, and those are the rows the player compares it with. That is the failure Nielsen Norman Group's tooltip guidance names first ("position tooltips so they don't block related content"). A cursor-anchored tooltip lands somewhere new on every hover, and on a dense list it covers the next row the pointer is moving to. The client's own bag frame already places an item tooltip beside the bag rather than over it, choosing the side by screen half (`wow-ui-source@297d7aaa:Interface/AddOns/Blizzard_UIPanels_Game/Mainline/ContainerFrame.lua:1448-1458`). The flat default `GameTooltip:SetOwner(frame, "ANCHOR_RIGHT")` puts the tooltip's bottom-left on the frame's top-right corner (warcraft.wiki.gg, *API types/TooltipAnchor*), which is the corner offset the owner ruled out.

**What it binds.** Every tooltip shown on hover or focus of an element of:

- an addon's standalone window, with every frame docked to it and the modal dialogs it opens;
- a **HUD display** (bars, icons, an icon grid and its chrome band, preview-mode);
- a window a library draws for the addon: the debug console and its copy window, the perf, sim and step panels, the icon browser, a `CopyWindow` (these follow the rule in the library's own code);
- an open dropdown menu the addon or `LibKa0s-Widgets-1.0` draws itself (not one the client's menu system draws; *What it does not bind*, below);
- the addon's minimap button (*The launcher*, below).

It binds `GameTooltip`, a tooltip frame the addon or a library creates, and a chart's hover alike.

**What it does not bind.**

- **Settings pages inside Blizzard's Settings canvas.** options-ui governs those pages, including the library's own Options widgets, and this section adds nothing to them.
- **A tooltip whose placement the client's own code decides (owner ruling of 2026-11-15, v2.112.1).** Blizzard's tooltips are out of scope, and the addon does not re-place them. That covers:
  - **an entry of a menu the client's menu system draws**, whose tooltip `MenuUtil.SetTooltip` or the menu code itself places: a `MenuUtil.CreateContextMenu` menu (the launcher's options menu, launcher-§2, among them) and the menu of a dropdown built on the client's dropdown templates;
  - **lines the addon adds to a tooltip the client anchors**: a unit or item tooltip over a Blizzard frame, written through `TooltipDataProcessor` or a hook.
- **A LibDataBroker display's bar** (Titan Panel, ChocolateBar and the like). The display draws the frame and places the tooltip, and the launcher object only fills it (launcher-§1).
- **Blizzard's own frames.** The addon only writes lines onto them.

**Terms.**

| Term | Meaning |
|---|---|
| **Body element** | Anything in the window's content: a row, a cell, a card, a list entry, a chart mark, and any control inside a row or a card (a row's action button, a card's mark). On a HUD display: a bar, an icon, a cell of an icon grid. **Every element the chrome row does not name is a body element**, so no element is left unclassified: a list's column-header row, a section heading, an empty-state line, a scroll bar, and the controls of a library window whose content is controls (a sim step panel's) are body elements (review ruling, flagged for the owner in the v2.112.0 changelog entry). |
| **Chrome element** | The title bar and every control on it; the test or sim strip; a tab; the filter bar and every control on it (a dropdown button, a search box, a button, a checkbox); the footer's text lines and marks (*The footer*, above); a toolbar, the band of controls the chrome order above places between the title bar and the body, and every control on it; the resize grip, in the footer's corner or, on a window with no footer, in the window's bottom-right corner. A HUD display's drag strip or mover handle is its title bar, and its test or sim strip is the strip, wherever preview-mode docks it. A modal dialog's controls are chrome too (orchestrator ruling, below). |
| **Window group** | The window plus every frame docked to it that moves with it, such as a companion panel, a side card or a drawer. The body rule places a tooltip outside the **whole group**. For a HUD display, the group is the **whole display**, all its bars or icons and its chrome (drag strip, mover handle, docked strip), and never the single bar or icon hovered. |
| **Outer edge** | The group's left or right edge on screen, its 1 px black edge included (*The Ka0s window edge*). |
| **Zone** | Which chrome band an element sits in. **Top chrome** is the title bar, the strip, the tabs, the filter bar and a toolbar, and a modal dialog's controls go with it. **Bottom chrome** is the footer and the resize grip. From v2.113.0 the zone no longer decides the vertical side, which is above in both (the chrome rule, below); it still names what counts as chrome, and no addon picks its own side. |
| **Gap** | **2 px**, between a tooltip and the edge or element it is placed against. It does not change with the skin (skinning-§4, *Geometry is skin-invariant*) and is published as `TIP_GAP` (*The library surface*, below). |

**The body rule (MUST).** A tooltip for a body element:

1. **Opens beside the window group, outside its outer edge.** It goes on the **right** when its width plus the gap fits between the group's right edge and the screen's right edge, and otherwise on the **left** of the group's left edge. A companion panel's own body tooltips prefer the panel's side **away from** the main window, so a panel docked on the main window's right puts its tooltips on its right; when that side does not fit, the tooltip goes outside the group's other outer edge, beyond the main window. Either way the tooltip sits outside the whole group. **The points:** on the right, the tooltip's `TOPLEFT` sits at the group's right outer edge plus 2 px, at the hovered element's top (`x = right + TIP_GAP`, `y = element top`); on the left, its `TOPRIGHT` sits at the group's left outer edge minus 2 px, at the same `y`. Edges and the tooltip's width are compared in one coordinate space (the screen's, `UIParent`, with each frame's effective scale applied), so a scaled window measures true.
2. **Has its top level with the hovered element's top.** It is clamped vertically so it stays on screen, sliding up from the screen's bottom or down from its top only as far as it needs to. The pointer never moves it.
3. **Never covers another frame of the same addon's window group.** A docked panel is part of the group, which is why rule 1 measures the group and not the frame under the pointer.
4. **When neither side fits** (the group spans the screen, or nearly), **falls back to the chrome rule on the hovered element**: attached, centered, 2 px above it, flipping below at the screen's top (orchestrator ruling; above since v2.113.0, as every attached tooltip is). This fallback is the one case in which a body tooltip is attached to its element.
5. **Extends its comparison tooltips outward.** An item tooltip's comparison tooltips (`ShoppingTooltip1`, `ShoppingTooltip2`) open further out on the **same side**, away from the window, never back over it (orchestrator ruling). The client's comparison manager picks their side from the tooltip's anchor type before it looks at screen room (`wow-ui-source@297d7aaa:Interface/AddOns/Blizzard_SharedXMLGame/Tooltip/TooltipComparisonManager.lua:91-101`). A placer that positions the tooltip with `ANCHOR_NONE` therefore **SHOULD** also call `tooltip:SetAnchorType("ANCHOR_RIGHT", 0, 0)` or `("ANCHOR_LEFT", 0, 0)` for the side it chose, as the client's bag does. Where the screen cannot hold the comparisons on that side, the client's own slide is accepted.
6. **An entry in an open dropdown menu the addon or `LibKa0s-Widgets-1.0` draws** follows this rule with the **menu frame** as its window: beside the menu, right when it fits and otherwise left, top level with the entry (orchestrator ruling). A menu the client's menu system draws, with its entries' tooltips placed by `MenuUtil.SetTooltip`, is out of scope (*What it does not bind*, above).

**The chrome rule (MUST).** A tooltip for a chrome element:

1. **Is attached to the element**, never to the cursor and never to the window's edge.
2. **Is horizontally centered on the element.** It is clamped to stay on screen, sliding sideways only as far as it needs to.
3. **Sits directly above the element, whatever chrome it is in** (title bar and its marks, strip, tabs, filter bar, toolbar, a modal dialog's controls, a HUD display's drag strip or mover handle, a footer line or mark, the resize grip): the tooltip's `BOTTOM` on the element's `TOP`, offset `0, TIP_GAP` (owner ruling of smoke round 1, 2026-11-16, v2.113.0; v2.112.0 placed top chrome and a modal's controls below).
4. **Flips below only when the screen has no room above**, with the same gap and the same centering: the tooltip's `TOP` on the element's `BOTTOM`, offset `0, -TIP_GAP`. With room on neither side it stays above.
5. **May cover the window's body.** A chrome tooltip opens over the body by design. It never covers the element it describes.

**The launcher (MUST).** The minimap button's tooltip is attached to the **button**, never to the cursor, and opens **toward the screen's center**, 2 px from the button. The vertical side follows the screen half the button's center is in (upper half: the tooltip below the button; lower half: above it), and the horizontal side the screen third (right third: the tooltip's right edge on the button's right edge, extending left; left third: left on left, extending right; middle third: centered on the button). **The points:** the tooltip's `<V><H>` on the button's `<opposite V><H>`, offset `0, -TIP_GAP` in the upper half and `0, TIP_GAP` in the lower, where `<V>` is `TOP` in the upper half and `BOTTOM` in the lower and `<H>` is `RIGHT`, `LEFT` or empty by third. A button in the top-right corner therefore opens down and to the left: the tooltip's `TOPRIGHT` on the button's `BOTTOMRIGHT`, 2 px under it. LibDBIcon-1.0 already places the tooltip in this shape (its `getAnchors`, `libs/LibDBIcon-1.0/LibDBIcon-1.0.lua:51-57` in the copy the collection vendors), but at 0 px. **That 0 px placement is compliant below `LibKa0s v1.105.0`** (orchestrator ruling: the launcher tooltip is drawn by the library, launcher-§1, so no host can add the gap without re-anchoring a tooltip it does not own); it is the one exception to the 2 px gap. From `LibKa0s v1.105.0` the launcher (Launcher minor 11) re-places LibDBIcon-1.0's tooltip on the addon's own button through `PlaceLauncher`, with the gap, so the exception ends at the addon's re-vendor of that tag with no addon code. A broker display's bar keeps its own anchor (*What it does not bind*, above). launcher-§7 states the same rule from the launcher's side.

**The library surface.** The rules are this standard's, and the placement code is `LibKa0s`'s. v2.112.0 named it **LibKa0s tooltip placement**, a future surface; it ships as the major **`LibKa0s-Tooltip-1.0`**, file `Tooltip.lua`, Tooltip minor 1, from **`LibKa0s v1.105.0`** (`docs/api/Tooltip/version-1-docs.md` in the library repo; library-stack-§7). It reads no other `LibKa0s` major and floors on none, and every caller reads it at call time. Its members:

- **`PlaceBeside(tip, el, group, opts)`**, the beside-the-window placer: the body rule's side choice, top alignment, clamp, fallback below the element and comparison anchor type (`SetAnchorType` before the point). `group` is a frame, a list of frames, `{ main, panels }`, a function answering one, or nil for **`GroupOf(el)`**; **`SetGroup(window, companions)`** registers a window and the frames docked to it, so a companion's tooltips open on its side away from the main window. A menu's entries pass the menu frame (body rule 6).
- **`PlaceAttached(tip, el, opts)`**, the attached-centered placer: the chrome rule's centering above the element, sideways clamp and flip below without room above. The first cut's `zone` argument (`"top"` below, `"bottom"` above) is retired before the tag; a string in that slot reads as no options.
- **`AttachTitleTip(btn, words, owner)`**, the title-bar tooltip hook (*Title-bar controls*, above), and the close's words: **`CLOSE_STRINGS`** (`CLOSE_TIP = "Close"`), **`SetCloseTip(owner, words)`** and **`CloseTip(owner)`**.
- **`PlaceLauncher(tip, button)`**, the launcher placer: toward the screen's center with the gap, the one relative anchor.
- **`TIP_GAP = 2`**, the gap; **`Own(tip, el, opts)`**, which owns a tooltip at `ANCHOR_NONE` before it is filled and shown; and **`Replace(tip)`**, which places it again after late growth.

A placement is applied after `Show()`, as one absolute point on `UIParent`, every edge read in screen units, so a scaled window measures true; a geometry read that is not a plain number, a secret included, places nothing, and the caller's fallback attaches the tooltip to its element, never to the cursor. The test kit's `mock_screen.lua` (kit revision 57) is the fake screen *Verification* below drives.

**When it binds (v2.113.0, owner ruling Q6 of 2026-11-16).** Moving an addon's own tooltips onto the placers is owed **when the addon adopts the surface**, tracked by LibKa0s#92, and not at its re-vendor to `LibKa0s v1.105.0` (library-stack-§7, *What a re-vendor owes and what adoption owes*). v2.112.0 wrote that every placement went through the placers from the re-vendor of the tag that ships them; that would have made every addon non-compliant the day it re-vendored, before any adoption could land, and is withdrawn. The rules themselves hold on every tag: a host-anchored tooltip that already matches them (beside the group with its top level with the row, or attached and centered above its control) is **compliant** before the addon adopts, and does not have to move to the library to stay so. So is a host chrome tooltip attached and centered **below** a top-chrome control, the side v2.112.0 required: it moves above when the addon adopts the surface (`PlaceAttached` puts it there), not before; a tooltip that breaks them is a finding now, on any tag (on the cursor, at a corner offset of a chrome control, or covering the window group). Once the addon has adopted the surface, a host placement beside the placers is anti-pattern #47 as well as #119 where it breaks a rule. A window the **library** draws is the library's to move, and `LibKa0s v1.105.0` moved them: the icon browser's cells and toolbar, the library's dropdown and context-menu entries, the reorder handle, the sim panel's controls and step rows, a drag strip and its marks (attached above), Charts' default tooltip, the skin picker's toolbar and the launcher's minimap tooltip.

**A tooltip placed any other way is anti-pattern #119.** That covers one on the cursor (`ANCHOR_CURSOR`, `ANCHOR_CURSOR_RIGHT`, an `OnUpdate` that follows `GetCursorPosition`, an `ANCHOR_PRESERVE` tooltip left wherever the pointer first put it); a corner offset from a chrome control (`ANCHOR_RIGHT`, `ANCHOR_TOPRIGHT`, `ANCHOR_TOPLEFT` and their mirrors on a tab, a title-bar mark or a footer line); a body tooltip on top of the window group, or attached to the hovered row outside rule 4's fallback; a HUD display's tooltip placed beside the single bar or icon rather than the whole display; a gap other than 2 px (LibDBIcon-1.0's own 0 px launcher placement excepted below `LibKa0s v1.105.0`, *The launcher*, above); and a launcher tooltip on the cursor.

- **Verification (SHOULD).** The headless suite **SHOULD** carry a case per placer the addon calls (or per host placement, before it adopts the surface), driving the fake screen (the kit's `mock_screen.lua`, revision 57) through a right-fits and a right-does-not-fit layout and asserting the side, the top alignment and the gap from the tooltip's recorded points. `docs/smoke-tests.md` **MUST** carry the in-game check: hover a row, a tab, a filter-bar control and a footer line in each window, and a bar of each HUD display, with the window near each screen edge, and confirm each tooltip opens where this section puts it.
