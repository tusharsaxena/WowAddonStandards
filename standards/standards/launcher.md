> Part of the **[Ka0s WoW Addon Standard](../STANDARDS.md)** — the split standard. Cross-references use the `filename-§N` form (see the index's section map).

## Launcher — the minimap button and the broker plugin

Every Ka0s addon **MUST** ship a **launcher**: a minimap button, and the same addon shown in a broker display (Titan Panel, ElvUI's data texts, Bazooka). This is the entry point for the player who does not remember a slash verb, and it is the surface on which the collection is most visibly one collection — eleven buttons around one minimap, each wearing its own logo, each answering a click the same way.

**It is ONE object, registered twice — not two features.** The addon creates a single **LibDataBroker-1.1** object and hands that object to **LibDBIcon-1.0**; LibDBIcon draws the minimap button from it, and any broker display that is installed draws its own row from the very same object. One `OnClick`, one icon, one label, one identity. An addon that builds a minimap button with its own click handler and a broker object with a second one has written the same feature twice and will drift on the next behavior change — that is **anti-pattern #81**.

### 1. One object, registered twice

- **MUST** create exactly **one** LibDataBroker-1.1 object, of `type = "launcher"`, and **MUST** register it with **LibDBIcon-1.0**. `"launcher"` is the reason rather than a label: a broker display reads `type` to decide what to draw, and `"data source"` promises a `text` value that updates, which this object does not have — it exists to be clicked. A display handed the wrong type draws an empty value cell beside the icon forever. Both libraries are vendored under `libs/` like every other (library-stack-§1/§3).
- **MUST** use the **same name** for both registrations, and that name is the addon's **folder name** (`BankLedger`, `PartyFrameEnhanced`). This is **not cosmetic**: LibDBIcon keys the button's **saved position** by that name, so renaming it — or spelling it differently on the two registrations — drops the position the player dragged the button to and puts the button back at the library's default angle, while a broker display labels the plugin with the other spelling. The folder name is chosen because it is the one name the addon cannot change without changing what the client loads.
- The object's `OnClick` is the **only** click implementation in the addon, and it is **the library's**: `LibKa0s-Launcher-1.0` sets it from the descriptor (launcher-§2). Both surfaces dispatch into it, so **launcher-§2 is satisfied on the minimap and in a broker display by construction** rather than by two implementations agreeing, and the right-click menu a broker row opens is the same menu the minimap button opens.
- The object's `icon` is the addon's own logo, the same file the TOC's `## IconTexture` names (launcher-§4).
- **MUST** set the object's **`label`** to the addon's **brand name in plain text** — **`Ka0s <Name>`** (`Ka0s Bank Ledger`, `Ka0s Party Frame Enhanced`, `Ka0s KickCD`). `label` is the string a broker display prints in its own row, and it prints it **beside the other ten**, so it is the single field that decides whether the collection reads as one collection in Titan Panel or as eleven unrelated addons that happen to be installed together. Across the eleven adoptions it came out three ways — `Absorb Tracker`, `Ka0s KickCD`, `Ka0s Pretty Chat` — because nothing said what it was. Two of the three already match this rule and the third does not, and a display sorting its plugins alphabetically files that one under `A` while the rest sit together under `K`.
  - **It is deliberately NOT the TOC's `## Title`.** A Title **may** carry color escapes and one does: Ka0s Pretty Chat's is `Ka0s |cffff0000P|cffff9900r|cffffff00e|…`. Handed to a display that draws the string raw, that addon's row splatters across a list in which every other row is plain text; handed to one that strips escapes, it arrives mangled instead. `label` therefore **MUST NOT** contain an escape sequence of any kind, and the two fields **MUST NOT** be wired to each other.
  - **It is not the folder name either.** The folder name is the registration **name** (the bullet above), which LibDBIcon keys the saved position by and which a player reads nowhere as prose: `PartyFrameEnhanced` is an identifier, `Ka0s Party Frame Enhanced` is a name. Two fields, two jobs.
  - A `label` that is an ad-hoc spelling, the escaped Title, or the folder name is **anti-pattern #84**.
- **MUST NOT** register the broker object conditionally, and there is deliberately **no setting** that enables or disables it. A broker display shows what it chooses to show, and it already offers the player a per-plugin toggle of its own; an addon that hides itself from a display is solving the display's problem in the wrong place, in a second settings row the player has to find first. The **minimap button** has a visibility row (launcher-§3); the **broker object** has none.
- **MUST** show a **status tooltip** on hover, on the minimap button and in a broker display alike, and it **MUST** be drawn by **`LibKa0s-Launcher-1.0`** from the launcher descriptor — **Launcher minor 3, `LibKa0s v1.57.0`** — never by the host. The tooltip is the one place a player can see, without opening anything, whether the addon is on, and it is **shown while the addon is disabled** too: that is when the question is most often asked, and a disabled addon's button answering nothing is indistinguishable from a broken one. Its shape is fixed, identical in all eleven addons, and top to bottom it is:

  ```
  <label>  v<version>             the object's label (launcher-§1); the version only where the descriptor passes one
  Enabled: Yes|No                 always; green for Yes, red for No
  Locked: Yes|No                  only where the addon has a lock and passes `isLocked`
  Test mode: On|Off               only where the addon has a test mode and passes `isTestMode`
  <the host's own lines>          optional, from the descriptor's `onTooltipShow`, appended here
  Left-click: Open settings       always, in either state
  Right-click: Options menu       always, in either state
  ```

  - **The status lines are the states the addon has, and no others.** *Enabled* is on every addon (slash-commands-§7). *Locked* appears only where the addon has a lock (the *Lock frame* row, options-ui-§15) and *Test mode* only where it has one (preview-mode); an addon without the state passes nothing and the line is absent, never drawn as a permanent *No*. Each state is **read on every show, never cached**, through the same accessor the Master-controls row reads, so the tooltip cannot disagree with the panel.
  - **The click hints are launcher-§2, stated, and they are the same two lines on every addon.** Left-click opens the settings panel and right-click opens the options menu, in either state, so neither hint varies by addon or changes while the addon is disabled; the menu itself shows what is available (its grayed entries, launcher-§2). **Since v2.67.0 (Launcher minor 4, `LibKa0s v1.58.0`)** the hints are fixed strings in the library's `lib.STRINGS`. The v2.66.0 hints they replace — a per-addon `Left-click: <leftClickLabel>`, its disabled form `Left-click: disabled — /<slash> enable`, and `Right-click: Open settings` — described launcher-§2's retired rungs, and `leftClickLabel` is retired with them.
  - **The host's own lines go BELOW the status block and ABOVE the hints, and nowhere else.** A host **MAY** pass `onTooltipShow`; the library appends what it adds, once, between the status lines and the click hints. It carries only what is the addon's own (a count, the current target, what the window holds). It **MUST NOT** draw a title, a version, a status line or a click hint of its own, since the library has drawn all four and a second copy is one that drifts; and the host **MUST NOT** set the LDB object's `OnTooltipShow` itself, which replaces the library's block wholesale. Either is **anti-pattern #89**, as is an addon whose button shows **no** tooltip, or none while disabled.
  - **Every string goes through the locale**: the library's `lib.STRINGS`, overridden by the descriptor's `L` (localization). The label is the object's plain-text `label` above, with no escape of its own; the only color is the green/red of the status values.
  - **Adoption is blocked until `LibKa0s v1.57.0` is tagged, and each addon's own next change owes it after that** (launcher-§5).

### 2. Click behavior — left-click opens settings, right-click opens the options menu

**The two buttons mean the same thing on every addon.** Left-click opens the settings panel; right-click opens a context menu of the toggles that addon has. Both are drawn and dispatched by **`LibKa0s-Launcher-1.0`** from the launcher descriptor — **Launcher minor 4, `LibKa0s v1.58.0`** — never by the host.

- **Left-click MUST open the settings panel**, on every addon, in either state. The panel is **setup**, not a feature (slash-commands-§7, *What MUST survive*), which is the same reason `config` and the bare `/<slash>` open it while disabled (slash-commands-§2). It goes through the descriptor's `openSettings`, the addon's one panel opener.
- **Right-click MUST open the options menu**: the client's own context menu (`MenuUtil.CreateContextMenu`, 11.0 and later), titled with the object's plain-text `label` (launcher-§1), listing **only the toggles the addon has**, in this order and no other:

  ```
  <label>
  [x] Enabled        always                                     isEnabled + setEnabled(bool)
  [ ] Locked         only where the addon has a lock            isLocked + toggleLock
  [ ] Test mode      only where the addon has a test mode       isTestMode + toggleTestMode
  [ ] Show window    only where the addon has a primary window  isWindowShown + toggleWindow
  ```

  - **Each entry is a checkbox showing the current state**, read from the descriptor's accessor every time the menu opens and never cached, so the menu cannot disagree with the panel or the tooltip.
  - **Clicking an entry toggles it through the addon's OWN handler**, the same one the slash verb and the panel row use: *Enabled* through the path `/<slash> enable` / `disable` write (slash-commands-§2), *Locked* through `lock` / `unlock` or the *Lock frame* row (slash-commands-§8, options-ui-§15), *Test mode* through `test` or the *Test mode* row (preview-mode), *Show window* through the window's own toggle (standalone-windows). The refusals, the combat rules and the chat messages are therefore the addon's, unchanged, and the menu holds **no state** of its own: it is one more surface onto one value, as `enable` / `disable` are onto the *Enable* row.
  - **An entry appears exactly when the addon has the state, and an addon that has it passes both halves** — the accessor and the toggle. *Enabled* is on every addon (slash-commands-§7). *Locked* is the *Lock frame* row's lock, *Test mode* the *Test mode* row's switch, and *Show window* the addon's **primary window** — the data browser, ledger, meter window or group popup the addon exists to show (standalone-windows), not a settings or export dialog. An entry for a state the addon does not have, drawn as a permanent *No*, is as wrong as a missing one.
  - **While the addon is DISABLED, *Enabled* stays clickable and the rest are grayed out** with the note **"enable the addon first"**. *Enabled* is the off switch and has to work in the off state, exactly as `/<slash> enable` does. *Locked*, *Test mode* and *Show window* drive features, which refuse while disabled (slash-commands-§7), so the library shows them **disabled rather than hidden** — the player still sees what the addon offers and what to do first — and a grayed entry calls **no** handler and **writes nothing**. The tooltip keeps showing in either state (launcher-§1).
- **The wording is the library's.** The entry labels, the note and both click hints live in the library's `lib.STRINGS`, overridden by the descriptor's `L` (localization), like the tooltip's.
- **There is no setting that reassigns either button**, and a host **MUST NOT** build its own menu or route clicks itself — no `OnClick` of its own on the LDB object, no `MenuUtil`, `EasyMenu` or dropdown-menu call of its own for the launcher. What the host supplies is the descriptor's accessor-and-toggle pairs; what the menu looks like and when an entry is grayed is the library's, so the eleven buttons cannot drift apart.
- **Each rostered addon's entries are recorded in `ADDONS.md`**, one column on the roster, so an audit reads which of *Locked* / *Test mode* / *Show window* the addon owes rather than re-deriving it from the addon's shape. A new addon lists its entries with its roster row.
- A left-click that does anything but open the settings panel, a right-click that does anything but open this menu, a host-built menu or click routing, and an entry toggled by a copy of the addon's handler rather than the handler itself are **anti-pattern #81**.

**This replaces the three-rung left-click (v2.52.0 – v2.66.0), and the rungs are retired everywhere.** Through v2.66.0 left-click followed a rule, first match wins — **(a)** toggle the primary window, **(b)** else toggle the preview switch (test mode, or lock/unlock where unlocking is the preview), **(c)** else open the settings panel — with right-click always on the panel and the rung recorded in `ADDONS.md`. The collection owner retired it on 2026-09-24, after the in-client smoke pass of the 2026-09-23 remediation: the left button meant a different thing on each addon, a player had to hover to learn which, and it reached **one** toggle, while an addon with a lock, a test mode and a window had three a player wanted. The menu reaches every toggle the addon has from one place, and the left button is back to one meaning. The descriptor's `onClick` and `leftClickLabel` are **retired** with the rungs; the library ignores them if passed, and a host still passing them is carrying dead configuration (launcher-§5).

### 3. Visibility — one row, and it is LibDBIcon's own table

The minimap button's visibility is a **Master controls** row (options-ui-§15), and its stored shape is **LibDBIcon's own `minimap` table** — the `hide` boolean LibDBIcon owns and writes when the player uses its own menu — **never** a second key alongside it.

- **MUST** store at `minimap.hide` in the addon's **global** store and hand that same table to LibDBIcon's `:Register(name, ldbObject, db.global.minimap)`. A parallel `minimap.show` or `showMinimapIcon` is a second copy of one state that has to be kept in step with a table a library also writes, and the day they disagree the button and the checkbox disagree (**anti-pattern #81**).
- **The scope is GLOBAL, and that is the decision rather than an accident of where the other rows live.** A minimap button belongs to the **installation**, not to a profile: a profile is how a player configures what an addon *draws*, while the ring of buttons around the minimap is furniture they arranged once. **Switching profiles MUST NOT move a player's buttons**, and profile-scoped the button would appear and vanish on a switch made for an entirely unrelated reason — and ride every profile copy besides. The global store is what makes that true, and it is where LibDBIcon's own `minimapPos` has to live for exactly the same reason, which is why the two are one table.
- **A player's minimap-button choice SURVIVES A RESET, and that is a PROPERTY of the setting — not a consequence of where it is stored.** Whether the button is shown is a **per-installation display preference**, in the same class as the **position** the player dragged it to, which LibDBIcon keeps in the very same table and which no reset in the collection touches. Nobody has ever wanted *reset my settings* to mean *and put the button back on my minimap, at the default angle*. So, stated rather than derived:
  - `minimap.hide` **MUST** survive **both** options-ui-§12's ***Reset all settings*** **and** a **page-scoped Defaults button**. Neither may un-hide the button, and neither may re-hide a shown one.
  - An addon whose reset **would otherwise reach the row MUST exempt that one row**, through whatever veto it already has — `skipRestoreAll` for the descriptor-driven walk (options-ui-§1), or the equivalent carve-out in a hand-written one. One row, named once; nothing else about either reset changes.
  - **Two shapes of addon are genuinely reached, and both are in the collection today.** An addon with **no `profile` section at all** — everything it stores is `db.global` — whose global reset empties the account-wide store **wholesale** and merges the declared defaults back (options-ui-§12's second form), which walks `minimap.hide` straight back to shown. And **any** addon whose **page-scoped Defaults** button on General walks every Master-controls row that declares a `default` and rewrites it, which reaches the row even where the profile is a real boundary.

  **This replaces a justification that did not hold, and the rule it justified is unchanged.** Until v2.54.0 this section *derived* the conclusion: *Reset all settings* is a profile reset, the table is global, therefore the reset cannot reach it. The premise is not universal — an addon may have no profile — and the argument was only ever about that **one control**, so a page's own **Defaults** button walked past it untouched. Two adoptions found this independently. What the button must do is exactly what it always had to do; what changed is that the requirement now rests on what kind of setting this is, so it holds against **every** reset an addon ships rather than against the single one the old sentence had in mind. **An addon that already adopted MUST re-check its resets against the two shapes above** — where one reaches the row, its behavior has to change.
- **Most of the collection already stores it globally.** **Bank Ledger** and **Loot History** use `db.global.minimap`; **Multi Meters** uses `db.profile.minimap` and is the outlier, which adoption normalizes with a migration (launcher-§5).
- The row's **label says shown** and the stored boolean **says hidden**, so the row's `get`/`set` invert. That is the whole cost of storing the library's own key, and it is cheaper than the alternative. The `set` goes through the addon's **single write seam** (options-ui-§1, architecture-§5) like every other row, and calls LibDBIcon's `Show` / `Hide` so the button follows the checkbox immediately rather than at the next reload.
- **The row's schema path reads in the row's own sense: `<root>.minimap.shown`.** The path is also the row's CLI name (slash-commands-§3), so a path spelled after the stored key made `/<slash> get <root>.minimap.hide` answer `true` while the button was on the minimap, and `set … false` hide it. The row therefore **MUST** be declared at `<root>.minimap.shown` (`global.minimap.shown`, or `minimap.shown` in an addon whose schema root is already the global store), with `get`/`set` closures that invert onto the stored `minimap.hide`. `/<slash> get <root>.minimap.shown` answers `true` while the button is visible. **Storage does not move.** The stored key stays LibDBIcon's `minimap.hide`, and a stored `shown` key is still **anti-pattern #81**: the new path names a row, and nothing is ever written at it. Nor is anything declared at it: the defaults keep only `minimap.hide`, and a `shown` default is the same second copy. The boot check that every row's path resolves against the defaults therefore skips this row and resolves the stored `<root>.minimap.hide` instead; that is architecture-§5's one closure-backed exemption, and with LibKa0s it needs only the host's `defaultsRoot` answering no root for the row, not a library change. The old `…minimap.hide` path is not kept as an alias; it answers the unknown-setting refusal like any other path no row declares. The reset exemption names the row by its new path. **Commencement: each addon's next release.** No SavedVariables migration and no `NS.SCHEMA_VERSION` bump is owed, because the stored key is where it was and an existing `hide = true` reads as `shown = false` with no code. The release notes **MUST** say that `/<slash> set <root>.minimap.hide <v>` became `/<slash> set <root>.minimap.shown <not v>`, because a player's macro is the one thing the rename can break.
- **Seeding or backfilling the table is already settled elsewhere and is not restated as a rule here.** Writing `minimap = { hide = false }` over the `minimap.hide` key the `…minimap.shown` row's closures store is a whole-section write over a schema row, and **architecture-§5** governs it — as it governs LibDBIcon's own `minimapPos` writes into the same table, which are the library's and need no register row. The declared default is what materializes the table; cite architecture-§5, not this section.
- The row's **position** in the canonical set is fixed and is stated, with its reason, in options-ui-§15.

### 4. The icon is the addon's own logo

One file is the addon's face in **three** places — the AddOns list (the TOC's `## IconTexture`), the minimap button and a broker display — so a player who has seen the addon once recognizes it in all three.

- **MUST** point `## IconTexture` at that file, and **MUST** give the LDB object's `icon` field the same path (toc-file-§1). **MUST NOT** use a Blizzard icon path or a numeric file id for either: a borrowed icon makes the addon look like something else in the one list where the player is choosing what to turn off (**anti-pattern #82**).
- The file itself — its path, its exact format and the recipe that generates it — is **layout-§4**, which owns shipped media. It is `media/logos/<addon>.logo.128.tga`, 128×128, uncompressed 32-bit.
- The settings panel's **landing-page logo is a different, larger asset and is unchanged** (options-ui-§5). Two files, two jobs: one is read by the client as an icon at icon size, the other is drawn by the panel at 300×300.

### 5. Adopting it

Every addon in the collection is **non-compliant with this section until it adopts**, which is normal and expected — the section is new.

**The library minor lands FIRST, and no addon can adopt before it does.** options-ui-§15 and §16 require the Master-controls set to be **composed** by `LibKa0s-Options-1.0`'s `MasterControls` composer and never hand-written, and that composer has **no minimap seam**: there is no spec key for the row and nothing emits it (`OptionsCompose.lua`, compose minor 6, as shipped in LibKa0s v1.38.0). An addon that adopted today could satisfy this section only by hand-writing the row, which is the one thing §15/§16 forbid — so the standard's own rules would be in contradiction until the seam exists.

The seam is **`LibKa0s v1.39.0` (compose minor 7)**: a **`minimapPath`** spec key on `MasterControls`, exactly parallel to the existing `testModePath`, emitting the unconditional **`Minimap button`** row; and *Test mode* moves **off** `startsLine` so the two pair on one line as `[Minimap button] [Test mode]`, which is the column order options-ui-§15 states. Until an addon carries that tag, its adoption is **blocked rather than overdue**, and an audit records it as blocked — the gap is upstream, not in the addon.

Adoption is then one changeset per addon:

1. Vendor **LibDataBroker-1.1** and **LibDBIcon-1.0** under `libs/` and list them in the TOC's `# Libraries` section (toc-file-§4).
2. Generate `media/logos/<addon>.logo.128.tga` by layout-§4's recipe from the `.png` source already beside it, and point `## IconTexture` at it (toc-file-§1).
3. Build the one LDB object through `LibKa0s-Launcher-1.0`, give it the icon and the descriptor launcher-§2 reads (`openSettings`, and the accessor-and-toggle pair for each state the addon has), and register it with LibDBIcon.
4. Re-vendor **LibKa0s v1.39.0 or later**, add the **Minimap button** row to the schema at `global.minimap.shown`, its closures inverting onto `db.global.minimap.hide` (launcher-§3), declare `minimapPath` on the `MasterControls` call so the composer emits the **Minimap button** row in its canonical position (options-ui-§15), and hand the same `minimap` table to LibDBIcon.
   - **An addon that already stores the table under `profile` migrates it.** `db.profile.minimap` → `db.global.minimap` is a stored-path move and takes the full savedvariables treatment — a new step in the migration runner and a raised `NS.SCHEMA_VERSION`, in the **same** change that moves the path — carrying the player's existing `hide` and `minimapPos` across so an adopted button does not jump back to the default angle. In the collection this is **Multi Meters** alone; Bank Ledger and Loot History already store globally and owe no migration.
5. Record the addon's menu entries in `ADDONS.md`, and document the launcher in `docs/settings-panel.md` (the row) and `docs/ARCHITECTURE.md` (the object and its owner).

**The status tooltip (v2.66.0) is a second, later adoption** on the same object. It needs `LibKa0s v1.57.0` (Launcher minor 3), and until that tag exists it is **blocked rather than overdue**. Then, per addon: re-vendor v1.57.0 or later; in the launcher's descriptor pass `isLocked` and `isTestMode` where the addon has the state, and `version` (the v2.66.0 adoption also passed `leftClickLabel` on rung (a)/(b), which v2.67.0 retires); move whatever the addon's own `onTooltipShow` drew into its host lines, deleting any title, version, status line or click hint it drew itself (launcher-§1, anti-pattern #89); and record the tooltip in `docs/settings-panel.md`'s launcher row.

**The click behavior and the options menu (v2.67.0) is a third adoption** on the same object. It needs `LibKa0s v1.58.0` (Launcher minor 4), and until that tag exists it is **blocked rather than overdue**. Then, per addon: re-vendor v1.58.0 or later; in the descriptor pass `setEnabled` beside `isEnabled`, and `toggleLock` / `toggleTestMode` / `toggleWindow` (with `isWindowShown`) for the states the addon has, each wired to the **same handler** its slash verb or window toggle already calls (launcher-§2); delete `onClick` and `leftClickLabel`; update `ADDONS.md`'s menu-entries column if the addon's entries differ from it; and record the new clicks in `docs/settings-panel.md`'s launcher row and the README's description of the minimap button.

An addon that has adopted the launcher but not yet the 128×128 logo ships a button that draws **nothing**, which is worse than the state before it adopted. Landing steps 2 and 3 together is therefore the obvious way to sequence the work, and it is **guidance, not a MUST of this section**: how a changeset is cut into commits is `versioning-git`'s subject, not this one's. What this section binds is the shipped state — a launcher registered with no icon file behind it is the finding, whatever the commit history looks like.
